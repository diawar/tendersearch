# ТЗ для ИИ-агента: обновить уже установленное приложение из GitHub

Дата: 5 ноября 2026 года. Репозиторий: https://github.com/diawar/tendersearch. Ветка: **`main`**, нижний регистр.

## Задача и ожидаемый результат

Обнови существующую распакованную или установленную версию приложения «Госзакупки» до актуального коммита `origin/main`. Сохрани пользователей, роли, подборки, рабочие этапы, личные заметки и цены, избранное, Telegram-привязки, документы, поисковую базу и настройки доступа. Собери образ, выполни миграции, обнови действующие службы и проверь результат. Это обновление существующей установки, а не создание новой пустой базы.

Не требуется доступ к компьютеру разработчика. Нужны доступ к **целевому** серверу/ПК и его Docker, право чтения приватного репозитория, существующие локальные файлы окружения. Если доступ к GitHub отсутствует, владелец должен настроить SSH-ключ или HTTPS-авторизацию через менеджер учётных данных. Не помещай токен в URL репозитория, команды, отчёт или коммит.

Этап, с которого продолжается разработка: коммит с сообщением **«в процессе реализации Рабочего пространства»**. Реализованы основные операции рабочего пространства; договор, поставка и оплата пока не имеют автоматического подтверждения по данным портала. Не считай эти этапы завершённой интеграцией.

## 1. Инвентаризация до изменения файлов

1. Найди реальный каталог установки и определи ОС. Прочитай применимые `AGENTS.md`, `README.md`, `compose.yaml`, используемые Compose-override-файлы и [общую инструкцию установки](AGENT_INSTALLATION.md).
2. Проверь `git --version`, `docker version`, `docker compose version`, `docker compose ls`, `docker ps`, `docker volume ls`.
3. Определи имя действующего Compose-проекта, образы, службы, пути bind-mount и тома PostgreSQL, документов и Redis. Для `docker inspect` запрашивай только нужные поля (`Mounts`, идентификатор образа, Compose-метки); не выводи `Env`.
4. Запиши текущий коммит, если есть `.git`, и идентификатор образа работающего `web`. Сохрани старый образ отдельным локальным тегом до пересборки. Зафиксируй, какие службы работали и какие были намеренно выключены, а также паузы индексаторов.
5. Определи способ внешнего доступа: reverse proxy, домен, отдельный `tunnel-web`, облачный туннель. Сохрани прежние параметры запуска и URL. Обновление только `web` не обновляет отдельный `tunnel-web`.

На компьютере разработчика каталог был `C:/Users/Dmitriy Small/Documents/ChatGPT/tenderbot`, проект — `tender-search`, образ — `tendersearch:local`. **На целевом сервере это могут быть другие значения.** В `compose.yaml` имя по умолчанию — `tendersearch`. Использование другого имени проекта может создать пустые тома вместо подключения прежних.

Во всех следующих командах используй один и тот же обнаруженный проект и полный набор его Compose/env-файлов. В примерах `PROJECT_NAME` и имена архивов нужно заменить реальными значениями. Для проверки конфигурации используй `config --quiet`; полную конфигурацию с секретами не печатай.

## 2. Получение кода

### Если распакованная версия является Git-репозиторием

Проверь:

```text
git status --short
git branch --show-current
git remote -v
git rev-parse HEAD
git fetch origin main
git rev-parse origin/main
```

Убедись, что `origin` указывает на нужный репозиторий. Сохрани SHA `origin/main` как целевой коммит этого обновления. При чистом рабочем дереве переключись на `main` и выполни `git merge --ff-only TARGET_SHA`, подставив сохранённый SHA. Это фиксирует конкретную версию, даже если удалённая ветка изменится позднее.

Если есть локальные изменения, сначала сохрани их отдельно: patch и копии новых файлов. Не добавляй секреты в Git. Разберись с назначением изменений и сохрани нужные серверные доработки; не выполняй принудительный reset. Если ветки разошлись, не обходи отказ `--ff-only`: требуется разбор расхождений. Не теряй существующую ветку и незакоммиченные изменения.

### Если это ZIP-архив без `.git`

Не выполняй `git init` и принудительное наложение файлов поверх старого приложения. Создай рядом отдельный чистый checkout:

```text
git clone --branch main --single-branch https://github.com/diawar/tendersearch.git NEW_RELEASE_DIRECTORY
```

Старую папку оставь для отката. Сверь локальные доработки и перенеси только необходимые файлы конфигурации: `.env`, реально используемые overrides, настройки домена/туннеля. Не заменяй их `.env.example` и не генерируй заново пароли. Отдельно проверь локальное хранилище документов, если оно подключено bind-mount, а не Docker-томом. Сохрани его прежний абсолютный путь либо корректно перенеси с проверкой размера и прав.

Запускай новую папку с **прежним Compose-проектом и теми же томами**. Проверь все относительные пути в overrides: после смены каталога они могут указывать в другое место. Скорректируй рабочую папку службы автозапуска/прокси, если она привязана к старому каталогу. Не удаляй старую папку автоматически.

## 3. Что сохранять и чего не делать

- `.env`, пароли PostgreSQL, `DJANGO_SECRET_KEY`, API-ключи и токен Telegram остаются локальными. Не выводи их и не коммить.
- Не запускай `scripts/setup_local.py` поверх рабочего окружения. Не меняй пароль PostgreSQL только в `.env` существующей БД.
- Не выполняй `docker compose down -v`, `docker system prune --volumes`, удаление томов, `git reset --hard` или `git clean` для обычного обновления.
- Не удаляй неизвестные orphan-контейнеры: это может быть действующий внешний доступ.
- Не запускай второй независимый Telegram-получатель с тем же токеном. Существующий экземпляр на этом сервере нужно обновить, а не дублировать.
- БИН компании настраивается отдельно для каждого пользователя. Не копируй БИН разработчика или тестовые значения в настройки владельца установки.

## 4. Сборка, резервная копия и окно обновления

Собери новый образ до остановки работающего приложения:

```text
docker compose -p PROJECT_NAME config --quiet
docker compose -p PROJECT_NAME build web
```

Команды выше и ниже сокращены: добавляй прежние `--env-file` и `-f` там, где они используются. При ошибке сборки не останавливай рабочую версию.

На время миграции прекрати запись: останови старые веб-процессы (включая внешний), фоновые задачи и индексаторы с достаточным временем для штатного завершения. Используй только реально существующие службы; `db` и `redis` оставь работающими. Пример для полного набора служб этой версии:

```text
docker compose -p PROJECT_NAME stop --timeout 120 web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
```

Отдельный `tunnel-web` останавливай с его Compose-файлом. В старой версии `collection-monitor` может ещё отсутствовать — не включай несуществующее имя в команду остановки.

Сделай свежий полный дамп PostgreSQL, сохрани его на хосте и проверь оглавление:

```text
docker compose -p PROJECT_NAME exec -T db pg_dump -U tender_search -d tender_search -Fc -f /tmp/before-workspace-UPDATE_ID.dump
docker compose -p PROJECT_NAME exec -T db pg_restore -l /tmp/before-workspace-UPDATE_ID.dump
docker compose -p PROJECT_NAME cp db:/tmp/before-workspace-UPDATE_ID.dump data/backups/before-workspace-UPDATE_ID.dump
```

Сначала создай `data/backups` средствами текущей ОС. Используй уникальный `UPDATE_ID`, чтобы не затереть прежнюю копию. Если имя БД/роль отличаются, подставь обнаруженные значения. Не перенаправляй бинарный `pg_dump` через PowerShell `>`; файл внутри контейнера и `compose cp` сохраняют бинарный формат.

Сохрани копию документов и используемых конфигураций по разделу резервного копирования `AGENT_INSTALLATION.md`. Запиши размеры, контрольные суммы и места хранения. Читаемость оглавления дампа не заменяет проверку восстановления в отдельной БД. При незавершённой/ошибочной копии не начинай миграцию и восстанови прежние работающие службы, если обновление приходится отложить.

## 5. Миграции и запуск

Обычное обновление не должно заново создавать администратора или менять его пароль. Используй `migrate`, а не первоначальную инициализацию:

```text
docker compose -p PROJECT_NAME run --rm --no-deps web python manage.py migrate --noinput
docker compose -p PROJECT_NAME run --rm --no-deps web python manage.py check
```

В этом пакете добавлены миграции `0016`–`0022`; Django сам применит отсутствующие в правильном порядке. Не используй `--fake`. Если сервер старее, выполни также требуемые его версией backfill-команды из общей инструкции; не запускай полный повторный сбор без причины.

Изменения данных при обновлении воронки:

- «Жду решение» объединяется с «Подали заявку».
- Известные исходы прежнего «Решения» переходят в «Выиграли»/«Проиграли».
- Новые лоты, уже отмеченные звездой, попадают в «Интересные».
- Существующая цена сама по себе не считается поданной заявкой. Черновик в «Интересных» остаётся редактируемым; цена уже поданной/продвинутой позиции фиксируется.
- Личные заметки сохраняются. Они принадлежат пользователю и лоту, а не отдельной вкладке.

После успешных миграций пересоздай службы на новом образе, сохранив намеренно отключённые службы выключенными:

```text
docker compose -p PROJECT_NAME up -d --no-deps --timeout 120 --wait --wait-timeout 120 web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
docker compose -p PROJECT_NAME exec -T web python manage.py check
docker compose -p PROJECT_NAME exec -T web python manage.py showmigrations core
docker compose -p PROJECT_NAME ps -a
```

Новый **`collection-monitor` обязателен** для автоматического обновления подборок, перехода в «Не участвовали» и планирования проверки итогов. Его задачи выполняет обычный `worker` (очередь `celery`). Отдельно пересоздай `tunnel-web`, если внешний доступ использует его. Новая сборка `web` сама по себе не обновляет уже работающие контейнеры остальных служб.

Если Telegram ещё не был настроен, не включай его произвольным токеном: сохрани существующую конфигурацию и укажи отсутствие подключения в отчёте. Индексаторы возобновляй только если они были приостановлены в рамках этого обслуживания; намеренную паузу владельца сохрани.

## 6. Проверка результата и критерии приёмки

1. `/health/` и `/login/` отвечают HTTP 200 по действующим адресам; авторизация, права обычного пользователя и администратора сохранены. Проверены и localhost/внутренний адрес, и внешний путь, если он используется.
2. `showmigrations core` показывает применённые миграции до `0022`; `manage.py check` не сообщает ошибок. В журналах нет ошибок неизвестных таблиц, незарегистрированных задач и повторяющихся сбоев старта.
3. Старые пользователи, подборки, избранное, заметки, цены и документы доступны. Количество записей и контрольные примеры сверены с состоянием до обновления. Неизменное число текущих лотов не обязательно: фоновые источники продолжают обновляться.
4. Раздел называется «Рабочее пространство». В скобках в меню — число уникальных видимых лотов всех собственных подборок, без дублей и данных других пользователей.
5. Этапы идут так: «Все лоты», «Интересные лоты», «Подали заявку», «Заключение договора», «Поставка», «Оплата», «Выиграли», «Проиграли», «Не участвовали». Ручных списков выбора этапа/исхода нет. Сортировки суммы и дат работают до пагинации.
6. В карточке интересного лота вводится цена **за единицу с НДС**. Новая цена автоматически пересчитывается по ставке **16%**, поля выбора ставки нет. Старые зафиксированные цены сохраняют записанную ставку. Арифметический пересчёт не выдаётся за подтверждение правил подачи неподтверждённой площадки.
7. «Подать цену» фиксирует цену и переводит лот в «Подали заявку». После этого видна неактивная кнопка «Подали заявку». На этом этапе «Отменить отметку» возвращает лот в «Интересные», разблокирует цену и выключает проверку итогов. После подтверждённого исхода/исполнения отмена недоступна. **Ни одна из этих кнопок не отправляет настоящую заявку на портал.**
8. Рядом с кнопкой есть ссылки на Госзакуп и объявление. Заметка доступна внутри карточки, до 10 000 символов, приватна для пользователя.
9. «Извлечь техспецификацию» показывает текст связанного PDF/DOCX/TXT в карточке. Общие файлы объявления помечены. OCR сканов и конвертация старого DOC не реализованы; это ограничение, а не основание подменять текст документа.
10. БИН компании доступен в личных настройках. Проверка итогов запускается после отметки о подаче; переходы в выигрыш/проигрыш требуют подтверждения по протоколу конкретного лота. Неизвестный формат, отсутствие своего БИН среди участников и неподдерживаемая площадка не означают проигрыш.
11. Просроченные неподанные новые/интересные лоты автоматически уходят в «Не участвовали»; поданные заявки этот переход не затрагивает. Снятие отметки о подаче исключает публикацию результата устаревшей фоновой проверки.

Проверки с созданием цен, сменой этапов или отправкой Telegram выполняй в отдельной тестовой БД/учётной записи. Не помечай настоящие лоты владельца поданными для проверки развёртывания. Для автоматических проверок можно запустить `python manage.py test tender_search.core --noinput` в отдельной тестовой БД через новый образ; предварительно убедись, что она не занята другой тестовой сессией.

## 7. Ошибки и откат

При ошибке миграций не запускай старые обработчики поверх частично изменённой схемы. Сохрани диагностику без секретов, установи состояние применённых миграций и причину. Не удаляй БД и не пытайся исправить проблему новой пустой установкой.

Откат одного образа допустим только при совместимости схемы. В частности, старый код создания `CollectionLot` нельзя без проверки возвращать поверх новых обязательных полей. Если нужен откат данных, используй сохранённые образ, код, дамп и документы согласованно; восстановление поверх рабочей БД требует отдельного подтверждения владельца, поскольку уничтожит последующие записи. Не удаляй резервные копии после первого успешного открытия страницы.

## 8. Финальный отчёт владельцу

Сообщи кратко: исходный и установленный SHA, каталог и Compose-проект, URL, состояние служб и миграций, где лежит проверенная резервная копия, что проверено, какие ограничения/ошибки остались. Отдельно укажи недоступность внешнего туннеля, API площадки или Telegram, если она обнаружена. Не утверждай, что реальная подача заявок, проверка договора или OCR уже работают. Пароли, токены и содержимое личных заметок в отчёт не включай.
