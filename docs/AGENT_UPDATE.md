# Обновление приложения Госзакупки на действующем сервере

ТЗ для агента на сервере. Дата: 11 ноября 2026 года. Приватный репозиторий: https://github.com/diawar/tendersearch. Ветка: `main`. Версия расширения в этом выпуске: `0.16.0`. Последняя миграция: `0047_document_pending_projection_index`.

## Результат обновления

Обновить существующую установку до выбранного коммита `origin/main`, сохранив пользователей, роли, настройки, Telegram-привязки, рабочие этапы, подборки, заметки, цены, поисковую базу и файлы документов. Обновить все действующие процессы приложения, а не только web. Это обновление рабочей базы, а не первоначальная установка.

Агенту нужны доступ к целевому серверу, Docker Compose и право чтения приватного GitHub-репозитория. Доступ к ПК разработчика не нужен. Получить код через настроенный deploy key или менеджер учётных данных; токены не помещать в URL, команды или отчёт. Сохранить серверный `.env`, домен, proxy и используемые overrides. Подробности первой установки и резервного копирования: [AGENT_INSTALLATION.md](AGENT_INSTALLATION.md).

## Что изменилось в выпуске

- Единый путь: «Интересные лоты» → «Подготовить заявку» → «Подготовка заявки». Цена, товар и реквизиты сохраняются одной формой. Кнопка в таблице называется «Сохранить в черновик на zakup.gov.kz».
- В подготовке видны шесть шагов: данные товара, открытие Госзакупа, реквизиты, добавление лота, описание товара, черновик готов. Шаг сохраняется в БД. Цвета обозначают выполнение, текущую работу, ожидание, ошибку и ещё не начатые шаги.
- Кнопки зависят от полноты данных, БИН, типа налогоплательщика, состава лота, срока приёма и состояния заполнения. Автоматическая очередь пропускает неготовые строки. Во время заполнения изменение подготовки и повторный запуск блокируются.
- Расширение последовательно создаёт или продолжает черновики, сохраняет реквизиты и описание товара; ожидает восстановления при временном сбое. Неопределённое создание требует проверки существующей заявки, повторное создание вслепую запрещено. Результат передаётся в приложение.
- Сохранённый черновик остаётся в «Подготовке заявки». Подписание, обеспечение, ввод цены на портале и отправка выполняются вручную. Проверка статуса «Подана» через расширение с передачей отчёта переводит лот в «Подали заявку» и фиксирует локальную цену. Постоянный автоматический опрос поданных заявок расширением пока не реализован. Проверка наличия черновиков сама по себе не подтверждает подачу.
- Проверка участия и итогов по БИН, переходы к договору, проигрышу или отсутствию участия выполняются только по подтверждённым данным конкретного лота. Неизвестный формат или недоступность источника сохраняют этап и причину проверки. Поздние этапы договора и исполнения не откатываются ранним отчётом.
- У каждого пользователя свои БИН, реквизиты, структурированный адрес и признак плательщика НДС. Для текущей новой цены используется НДС 16% либо 0% по настройке организации. Цена без НДС сравнивается с подтверждёнными бюджетами за единицу и всего лота; превышение блокируется, снижение на 10% и более требует подтверждения. Эта отметка не гарантирует допуск на портале. Старые зафиксированные цены сохраняют свою ставку.
- Количество, бюджет за единицу и общая сумма одинаково видны в поиске, избранном, воронках и карточке. Неподтверждённые количество и цена явно отмечены.
- Добавлены данные доставки курьером с трек-номером либо своими силами, прикрепление акта и переход к оплате. Заключение основного договора проверяется по доступным подтверждённым данным Госзакупа; дополнительные соглашения и другие площадки не считать автоматически поддержанными.
- Массово загружаются только техспецификации активных закупок для поиска по документам. Прогресс первого заполнения показывается администратору в блоке базы. Другие документы загружаются по запросу. Хранение общее; очистка учитывает работу всех пользователей. Файлы договоров и актов также подлежат последующему удалению по правилам хранения, архив не означает бессрочное хранение файлов.

## Инвентаризация сервера

1. Найти каталог установки, прочитать применимые `AGENTS.md`, `README.md`, Compose-файлы и локальные инструкции сервера.
2. Проверить `git status --short`, `git rev-parse HEAD`, `git branch --show-current`, `docker compose ls`, `docker ps`, `docker volume ls`.
3. Зафиксировать имя действующего Compose-проекта, состав запущенных служб, image ID, тома PostgreSQL, документов и Redis, абсолютные пути bind mounts. Не печатать `Env` из inspect или полную Compose-конфигурацию с секретами.
4. Определить внешний доступ: reverse proxy, домен, tunnel либо отдельный `tunnel-web`. Сохранить прежний URL и все параметры запуска. Намеренно выключенные службы и паузы владельца сохранить.
5. Проверить свободное место для нового образа и резервных копий. Ориентир для самой установки после наполнения документов — 8–12 ГБ; для ОС, обновлений и резервных копий нужен дополнительный запас.

В локальной разработке проект назывался `tender-search`, образ — `tendersearch:local`. В Compose имя по умолчанию — `tendersearch`. На сервере определить фактические значения: смена имени проекта может подключить пустые тома вместо рабочих.

Во всех командах ниже заменить `PROJECT_NAME`, `TARGET_SHA` и `UPDATE_ID` фактическими значениями. Во все вызовы `docker compose` добавить тот же полный набор `--env-file` и `-f`, что использует действующая установка. Команды ниже показывают базовую форму, а не разрешение игнорировать серверные overrides.

## Получение версии из GitHub

Для установки с `.git`:

```text
git status --short
git remote -v
git fetch origin main
git rev-parse origin/main
```

Сохранить SHA `origin/main` как `TARGET_SHA`. На чистом рабочем дереве переключиться на `main` и выполнить:

```text
git switch main
git merge --ff-only TARGET_SHA
```

Локальные изменения предварительно сохранить отдельным patch и копиями новых файлов, затем согласовать с кодом выпуска. Не выполнять `reset --hard` или `clean`. При расхождении веток разобрать его, не обходить отказ `--ff-only`.

Если сервер развёрнут из ZIP без `.git`, создать рядом новый checkout:

```text
git clone --branch main --single-branch https://github.com/diawar/tendersearch.git NEW_RELEASE_DIRECTORY
```

Сохранить старую папку. В новый каталог перенести необходимые серверные конфигурации, а хранилища подключить прежние. Не переносить файлы окружения разработчика. Проверить относительные пути в overrides и рабочий каталог автозапуска. Продолжать с прежним Compose-проектом и теми же рабочими томами.

## Сборка и резервная копия

Сохранить старый образ под отдельным локальным тегом и записать исходный SHA. Сначала собрать новую версию, пока старая ещё работает:

```text
docker compose -p PROJECT_NAME config --quiet
docker compose -p PROJECT_NAME build web
```

При ошибке сборки оставить действующую версию работающей. Не применять первоначальную настройку, не запускать `setup_local.py` и не менять пароли существующей БД.

Перед миграциями согласованно остановить запись: web, внешние web-процессы, workers, мониторинг, индексаторы и Telegram. Останавливать только обнаруженные службы приложения; PostgreSQL и Redis оставить работающими. При наличии всех основных служб:

```text
docker compose -p PROJECT_NAME stop --timeout 120 web worker search-worker specification-worker product-analysis-worker indexer detail-indexer collection-monitor medical-indexer coverage-monitor telegram
```

Если используется `tunnel-web`, остановить и его с теми же параметрами Compose. Не завершать произвольные контейнеры других проектов.

Создать каталог `data/backups` средствами текущей ОС. Сделать дамп внутри контейнера и скопировать бинарный файл через Compose:

```text
docker compose -p PROJECT_NAME exec -T db pg_dump -U tender_search -d tender_search -Fc -f /tmp/before-UPDATE_ID.dump
docker compose -p PROJECT_NAME exec -T db pg_restore -l /tmp/before-UPDATE_ID.dump
docker compose -p PROJECT_NAME cp db:/tmp/before-UPDATE_ID.dump data/backups/before-UPDATE_ID.dump
```

При иной БД или роли подставить серверные значения. Не перенаправлять бинарный дамп через PowerShell `>`. Сохранить также документы и конфигурацию по инструкции резервного копирования, записать размеры, контрольные суммы и пути. Проверка оглавления дампа не заменяет пробное восстановление в отдельной БД. Если резервная копия не готова, миграции не начинать.

## Миграции и перезапуск

```text
docker compose -p PROJECT_NAME run --rm --no-deps -T web python manage.py migrate --noinput
docker compose -p PROJECT_NAME run --rm --no-deps -T web python manage.py check
docker compose -p PROJECT_NAME run --rm --no-deps -T web python manage.py showmigrations core
```

Применить все отсутствующие миграции, включая `0032`–`0047`, без `--fake`. Миграция `0039_unify_submission_path` возвращает старую ручную отметку «Подали заявку» в «Подготовку заявки», если нет сохранённого подтверждения портала `submitted` или `completed`; разблокирует её локальную цену и создаёт пункт очереди. Это ожидаемое изменение данных выпуска. Миграция `0040` добавляет сохранение шага подготовки. Не делать собственных массовых подстановок статусов, БИН и цен.

Миграция `0045` заполняет пустые реквизиты предусмотренными в выпуске значениями OVERSHOP.KZ и задаёт их новым пользователям; телефон не копируется, заполненные реквизиты других организаций сохраняются. Дополнительную массовую перезапись не выполнять. Проверить настройки нескольких пользователей: значение по умолчанию не подтверждает фактический налоговый статус организации.

После успешной миграции пересоздать действующие службы новым образом:

```text
docker compose -p PROJECT_NAME up -d --no-deps --timeout 120 --wait --wait-timeout 120 web worker search-worker specification-worker product-analysis-worker indexer detail-indexer collection-monitor medical-indexer coverage-monitor telegram
docker compose -p PROJECT_NAME exec -T web python manage.py check
docker compose -p PROJECT_NAME exec -T web python manage.py showmigrations core
docker compose -p PROJECT_NAME ps -a
```

Добавить внешний `tunnel-web`, если он используется; намеренно остановленные службы из команды исключить. `collection-monitor` и обычный `worker` нужны для автоматических переходов, планирования поиска по техспецификациям и очистки документов. `detail-indexer` обновляет подробности отдельно от быстрого обхода реестров. Существующие контейнеры других служб не обновятся от одной пересборки web.

У основного сервера оставить его собственную настройку `TELEGRAM_POLLING_ENABLED=true`: один бот должен иметь единственного получателя входящих сообщений. Локальная копия разработчика с тем же ботом использует `false` и только отправляет уведомления. Не перезаписывать серверное окружение локальным и не запускать второй receiver. Независимые БД не синхронизируют Telegram-привязки автоматически.

## Обновление расширения Chrome

1. Открыть настройки обновлённого приложения по его серверному адресу и скачать расширение `0.16.0` из раздела установки. Архив из своего экземпляра содержит его разрешённый адрес; не использовать сборку, настроенную на `localhost`, для другого домена.
2. Остановить активное заполнение. В `chrome://extensions` обновить распакованную сборку либо загрузить новую папку, сохранив журнал восстановления и номера черновиков. Проверить версию и разрешения сайта.
3. Перезагрузить страницы подготовки и очереди в этом Chrome. Войти на Госзакуп самостоятельно через ЭЦП. ЭЦП, пароли и cookies на сервер не переносить.
4. Проверить связь с приложением и отображение шагов без создания настоящей заявки. Реальное создание тестового черновика выполнять только с отдельным разрешением владельца для указанного лота. Подписание, отправку, обеспечение и удаление заявок не выполнять при проверке обновления.

Очередь выполняется в авторизованном Chrome, а не на сервере. Страница подготовки очереди должна оставаться открытой. Нельзя гарантировать продолжение заполнения при закрытом браузере. После восстановления связи проверяется существующий черновик; журнал нельзя удалять для обхода защиты от дублей.

Миграция `0041` добавляет отдельную очередь `WorkflowDelivery` для подтверждённых событий подачи, подписания договора и полной оплаты. Таблица создаётся без рассылки исторических событий. Для работы новых уведомлений обновить web, worker, telegram и collection-monitor; локальный режим получения сообщений остаётся выключенным. Первое чтение статуса и автоматическое отключение слежения больше не создают служебные Telegram-сообщения. После `/stop` или отключения в настройках ожидающие сообщения всех четырёх очередей отменяются; старые отменённые сообщения не восстанавливать.

Миграция `0042` добавляет непрозрачный токен кнопки «В интересные» в Telegram-уведомлениях о новых закупках. Обновить основную копию, получающую `callback_query`: кнопка сверяет получателя, конкретное отправленное сообщение и токен. Нажатие добавляет звезду и слежение, но не возвращает назад лоты с последующих этапов и не переносит закрытые лоты. В старые уже отправленные сообщения кнопка не добавляется. Локальная send-only копия не должна становиться вторым получателем; сообщения разных независимых БД не считать взаимозаменяемыми.

## Проверки после обновления

- Внутренний и внешний `/health/` отвечают 200. Вход, роли и доступ к данным владельцев сохранены. Блок базы закупок и администрирование доступны только администраторам.
- Миграции до `0047_document_pending_projection_index` применены. В логах нет ошибок схемы, отсутствующих задач и повторяющихся падений служб. Логи проверять с сокрытием секретов.
- Сверить сохранённые пользователи, профили, заметки, цены, файлы и несколько контрольных лотов с резервной копией. Изменение числа активных лотов из-за обновления источников само по себе не ошибка.
- Воронка: «Неразобранные лоты», «Интересные лоты», «Подготовка заявки», «Подали заявку», «Заключение договора», «Поставка», «Оплата», «Выиграли», «Проиграли», «Не участвовали», «Архив». Звезда и самолётик одинаковы во всех представлениях пользователя.
- В поиске, избранном и воронках одинаково показаны сумма, количество и бюджет за единицу. Сортировки выполняются до пагинации. В поиске и рабочем пространстве доступны размеры страниц 10/20/50/100.
- В карточке неразобранного лота после техспецификации доступны «В интересные» и «Неинтересно». В интересном лоте синяя кнопка «В подготовку заявки» находится после техспецификации. Переходы не подменяют реальную подачу.
- В подготовке видны количество и бюджет; цена и реквизиты сохраняются вместе. В отдельной тестовой БД проверить оба режима НДС: при бюджете 100 ₸ без НДС цена 116 ₸ с НДС или 100 ₸ у неплательщика проходит, 116,01/100,01 блокируется; 104,40/90 требует подтверждения снижения. Не менять настоящие пользовательские настройки ради этой проверки.
- При отсутствии обязательных данных сохранение черновика заблокировано, причина видна. Готовые лоты доступны к запуску. Во время заполнения нельзя изменить подготовку, повторно запустить или вернуть лот в интересные. Последний шаг сохраняется после перезагрузки.
- Ручные переходы «К договору», «Договор заключён», «Оплата получена» отсутствуют в интерфейсе и запрещены сервером. Старый маршрут тестовой отмены подачи удалён (404). Загрузка акта переводит к оплате; архивирование после полной оплаты выполняется только по подтверждённым данным проверки договора. Архивирование завершённых исходов и восстановление из архива остаются ручными.
- Номер черновика и «Черновик готов» не переводят лот в «Подали заявку». Подтверждённый отчёт «Подана» включает этот этап и блокирует цену. Непонятный ответ или недоступность портала не считать доказательством подачи, отсутствия участия или проигрыша.
- Поиск в техспецификациях использует загруженный текст. Первый индекс считается наполненным по состоянию прогресса, а не одному числу файлов. OCR сканов и старый DOC не объявлять поддержанными; PDF/DOCX/TXT проверять отдельно.
- Файлы и их очистка общие для пользователей; активная работа другого пользователя удерживает нужный файл. Архив прекращает активные проверки и не означает бессрочное хранение файлов. Не запускать ручное массовое удаление при установке.

Автоматические проверки запускать в отдельной тестовой БД, а не на рабочих пользователях:

```text
node tests/draft_queue_ui.test.cjs
node tests/draft_queue_auto_ui.test.cjs
node tests/preparation_bridge_ui.test.cjs
node tests/preparation_price.test.cjs
node tests/structured_address.test.cjs
node extensions/goszakup-assistant/draft.test.cjs
node extensions/goszakup-assistant/popup.test.cjs
```

Проверка без удаления: `docker compose run --rm web python manage.py cleanup_archived_lots --dry-run`. Очистку выполняет работающий collection-monitor; ручной запуск `cleanup_archived_lots` удаляет данные по тем же правилам. Заявки на портале и внешние сообщения Telegram не изменяются.


### Защита очистки от параллельных операций

Изменения не требуют новой миграции поверх `0054_archive_retention`. Пересобрать и обновить web, worker, specification-worker и collection-monitor, а также остальные сервисы того же образа. Очистка общих документов и изменение потребности пользователей синхронизируются блокировкой объявления. Публикация скачанного файла и сохранение ссылки в БД защищены PostgreSQL-блокировкой пути; скачивание идёт во временный каталог `document-staging` на том же хранилище. Все экземпляры приложения должны использовать одну БД и общий том документов.

Загрузка личного акта заранее сохраняет запись на очистку; запись переживает откат транзакции. Заменённые акты удаляются через очередь с повтором при сбое хранилища. Часовая очистка также подбирает старые файлы из `private-acts`, которые больше суток не имеют ссылки из LotShipment; файлы с действующей ссылкой любого пользователя сохраняются.

### Калькулятор и подбор товара

Сохранённые товар, закупка, цена продажи, доставка, дополнительные расходы, заметки, подготовка и акты привязаны к пользователю. Общими остаются документы закупки. Не переносить личные расчёты или акты между пользователями при обновлении. Товар, закупка и цена продажи фиксируются с этапа «Заключение договора»; доставка редактируется до этапа «Оплата».

Калькулятор использует доставку «От двери до двери», товар и цену из подготовки; дополнительные расходы добавляются кнопкой «+». Подбор расходников для лота с МФУ/принтером отсеивается до сравнения. Ручная подстановка кандидата требует подтверждения каждого неподтверждённого требования и не снимает ограничения по бюджету, наличию, количеству или явным несоответствиям.

Telegram больше не отправляет уведомление «Не участвовали»; автоматический переход в этот этап сохраняется. Ранее накопленные сообщения об отсутствии участия отменяются при обработке очереди уведомлений.

Пересобрать образ и обновить все работающие сервисы приложения, включая `product-analysis-worker`, `specification-worker`, `worker`, `web` и `collection-monitor`. Само получение кода из GitHub не обновляет запущенные контейнеры. Настройки серверного Telegram-получателя сохранить; локальная копия может работать только на отправку.
