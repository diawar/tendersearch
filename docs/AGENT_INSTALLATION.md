# Инструкция ИИ-агенту: установка и обновление «Госзакупки» из GitHub

Дата актуализации: 5 ноября 2026 года.
Репозиторий: https://github.com/diawar/tendersearch
Ветка: `main` (нижний регистр).
Для уже распакованной или установленной версии используй [ТЗ по обновлению](AGENT_UPDATE.md). Перед обновлением зафиксируй фактический SHA `origin/main`; приведённые ниже общие шаги сверяй с этим коммитом.

## 1. Задание агенту

Разверни веб-приложение «Госзакупки» из указанного репозитория на целевом компьютере или сервере. Выполни настройку, сборку Docker, миграции, запуск и проверки. В конце сообщи адрес приложения, установленный коммит, состояние служб и незавершённые действия. Пароли и токены в отчёт не включай.

Перед выполнением определи:

- ОС, каталог установки и доступ к Docker.
- Это новая независимая установка, обновление существующей или перенос с другого компьютера.
- Нужны ли прежние пользователи, подборки, избранное, Telegram-привязки и документы.
- Нужен ли только локальный доступ или есть домен для HTTPS.
- Будет ли подключён Telegram-бот; где владелец сохранит его токен.

Если этих сведений нет в окружении, уточни только недостающие. Не используй пароли из истории переписки. Не создавай новый репозиторий: используй существующий.

Прежде чем выполнять команды, прочитай актуальные `README.md`, `compose.yaml`, `.env.example`, `src/tender_search/web/settings.py`, `scripts/setup_local.py` и применимые `AGENTS.md`, если они существуют. Эта инструкция описывает проверенный коммит; при изменении `main` сверяй команды с кодом.

## 2. Что находится в Git и что переносится отдельно

Git содержит код, шаблоны, статические файлы, миграции и конфигурацию сборки. В нём нет рабочей БД, секретов, документов и данных пользователей.

| Компонент | Где хранится |
| --- | --- |
| PostgreSQL: пользователи, подборки, избранное, привязки Telegram, лоты | Docker-том `database` соответствующего Compose-проекта |
| Скачанные документы | Docker-том `documents`, смонтирован в `/app/data`; документы в `/app/data/documents` |
| Redis и очередь задач | Docker-том `queue` |
| Пароли и токены | Локальный `.env`, при наличии — другие локальные файлы окружения |
| Первоначальные данные входа | Локальный `data/first-login.txt` |

Не публикуй эти данные в Git. Не выводи `.env`, токены, пароли и полную конфигурацию окружения в чат или журналы. Для проверки синтаксиса Compose используй `docker compose config --quiet`, а не вывод всей конфигурации.

## 3. Сохранение существующей установки

Перед обновлением выполни `docker compose ls`, `docker ps` и `docker volume ls`. Определи имя действующего проекта и фактические тома; при необходимости смотри только поле `Mounts` через `docker inspect`.

В текущей рабочей установке на компьютере владельца:

- каталог: `C:/Users/Dmitriy Small/Documents/ChatGPT/tenderbot`;
- Compose-проект: `tender-search`;
- образ: `tendersearch:local`;
- тома: `tender-search_database`, `tender-search_documents`, `tender-search_queue`;
- в локальном `.env` задано `COMPOSE_PROJECT_NAME=tender-search`.

В репозитории `compose.yaml` по умолчанию задаёт другое имя: `tendersearch`. Если забыть старое имя проекта, Docker может создать отдельные пустые тома: прежние данные будут выглядеть потерянными.

Для существующей установки сохраняй её `COMPOSE_PROJECT_NAME` либо явно добавляй `-p ИМЯ_ПРОЕКТА` ко всем командам Compose. Примеры ниже используют `docker compose` и предполагают, что правильное имя уже задано. На новом независимом сервере можно использовать имя по умолчанию `tendersearch`.

Не выполняй `docker compose down -v`, удаление томов, `docker system prune --volumes`, `git reset --hard` или `git clean` для обычного обновления. Не меняй пароль PostgreSQL только в `.env` у существующего тома: это не меняет пароль внутри БД.

## 4. Требования к целевому окружению

- Git и доступ к репозиторию. Для закрытого репозитория используй настроенную SSH/HTTPS-авторизацию, без токена в URL.
- Python 3.11+ на хосте для `scripts/setup_local.py`; приложение работает на Python 3.12 внутри образа.
- Docker Engine с Compose v2; на Windows — работающий Docker Desktop с Linux-контейнерами/WSL 2.
- Доступ к Docker Hub и источникам закупок; для Telegram — к API Telegram.
- Свободное место для образов, PostgreSQL, документов и резервных копий. Перед переносом измерь исходные объёмы и учти место для распаковки и одновременного хранения резервной копии.
- На сервере настрой автоматический запуск Docker после перезагрузки; на рабочем компьютере проверь запуск Docker Desktop.

Проверь:

```text
git --version
docker version
docker compose version
```

Если Docker не запущен или нет прав доступа, сначала устрани это. Не запускай вторую независимую копию приложения в случайном каталоге.

## 5. Новая установка с пустой базой

### 5.1. Получить код

В родительском каталоге установки:

```text
git clone --branch main https://github.com/diawar/tendersearch.git
cd tendersearch
git status --short
git rev-parse HEAD
```

Если каталог уже содержит проект, сначала проверь изменения и `origin`. Не выполняй clone поверх существующих файлов. Обновление описано отдельно ниже.

### 5.2. Создать локальную конфигурацию

Windows:

```powershell
python scripts/setup_local.py
```

Linux:

```bash
python3 scripts/setup_local.py
chmod 600 .env data/first-login.txt
```

Скрипт создаёт случайные секреты и пароль первого администратора `admin`. Если `.env` уже существует, он ничего не перезаписывает. Проверь наличие обязательных настроек без вывода их значений. Существующий неполный `.env` нужно дополнить вручную, не генерируя заново рабочие секреты.

`data/first-login.txt` содержит секрет: укажи владельцу путь к файлу, не публикуй его содержимое. В проверенной версии текст этого файла ещё содержит старое название TenderSearch и устаревшую строку об отключённой админке; фактически управление пользователями доступно в `/administration/`.

Для локального HTTP оставь `DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,[::1]` и `WEB_PORT=8000`, если порт свободен. Не включай HTTPS-cookie для обычного HTTP-входа.

### 5.3. Собрать и запустить

```text
docker compose config --quiet
docker compose build web
docker compose up -d --wait db redis
docker compose run --rm --no-deps initialize
docker compose up -d --no-deps --wait web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
docker compose exec -T web python manage.py sync_references
docker compose exec -T web python manage.py sync_cities
```

Проверяй код завершения каждого шага. Не продолжай запуск после ошибки миграций.

`initialize` применяет миграции и создаёт первого администратора. Для существующего активного администратора пароль сохраняется. Завершение этой одноразовой службы с кодом 0 — нормальное состояние.

Образ общий для всех служб приложения: отдельная сборка каждого worker не нужна. Исходники не подключены как редактируемый том; изменение файлов на хосте требует пересборки образа.

Локальный адрес: http://localhost:8000/ (либо выбранный `WEB_PORT`).

## 6. Доступ через домен и HTTPS на сервере

Основной Compose публикует веб-порт только на `127.0.0.1`. Для внешнего доступа используй reverse proxy с TLS. PostgreSQL и Redis не публикуй наружу.

Пример для proxy на том же Linux-хосте: домен направлен на сервер, Nginx/Caddy принимает HTTPS и передаёт запросы на `127.0.0.1:8000`. Proxy должен передавать исходный `Host`, `X-Forwarded-Proto: https`, адрес клиента и сам задавать доверенные forwarding-заголовки. Доступ к backend должен оставаться только через доверенный proxy.

Добавление только `HTTPS_ENABLED` в `.env` недостаточно: основной Compose не передаёт этот параметр контейнеру. Создай локальный `data/compose.production.yaml`:

```yaml
services:
  web:
    environment:
      DJANGO_ALLOWED_HOSTS: ${APP_DOMAIN},localhost,127.0.0.1
      CSRF_TRUSTED_ORIGINS: https://${APP_DOMAIN}
      HTTPS_ENABLED: "1"
    command: [gunicorn, tender_search.web.wsgi:application, --bind, "0.0.0.0:8000", --workers, "1", --threads, "2", --timeout, "60", --forwarded-allow-ips, "*", --access-logfile, "-"]
```

В `.env` добавь `APP_DOMAIN=фактический.домен` без протокола. Такой `forwarded-allow-ips` допустим только при изоляции backend за доверенным proxy; не сочетай пример с открытым публичным портом Gunicorn. В существующей инфраструктуре согласуй модель доверия proxy с её конфигурацией.

Для проверки, запуска и последующих обновлений используй одинаковый набор файлов:

```text
docker compose -f compose.yaml -f data/compose.production.yaml config --quiet
docker compose -f compose.yaml -f data/compose.production.yaml up -d --no-deps --wait web
```

При последующих командах `up` также указывай этот override, иначе параметры HTTPS могут потеряться. После включения secure-cookie проверяй вход через HTTPS-домен, а не через HTTP localhost.

Настрой сертификат и HTTP→HTTPS перенаправление на proxy, проверь продление сертификата. Не объявляй установку доступной извне до проверки домена, сертификата и POST-запросов входа/сохранения.

`compose.tunnel.yaml` — отдельный вариант временного доступа. Он не запускает сам туннель и требует `TUNNEL_HOST` и отдельной настройки. Не подменяй постоянное серверное размещение случайным временным туннелем.

## 7. Telegram

Если Telegram требуется, владелец сохраняет `TELEGRAM_BOT_TOKEN` и `TELEGRAM_BOT_USERNAME` в локальном `.env`. Не запрашивай токен в публичном чате.

После изменения окружения пересоздай службы, которым основной Compose передаёт токен:

```text
docker compose up -d --no-deps web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
```

При наличии production override используй и его. Для независимой установки нужен отдельный бот. При переносе одного бота останови старый `telegram`, прежде чем запускать новый: два процесса не должны одновременно получать обновления одного бота.

Пользователь подключает Telegram в настройках приложения. Уведомления включаются отдельно у подборок/избранного. Отправляй тестовое сообщение только по разрешению владельца.

## 8. Резервная копия перед обновлением или переносом

Создай `data/backups` средствами ОС (`New-Item` на PowerShell или `mkdir -p` на Linux). Выбери уникальное имя копии; не перезаписывай предыдущую.

Сначала останови все процессы приложения, которые могут менять данные. БД и Redis оставь работающими:

```text
docker compose stop -t 120 web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
```

Если есть `tunnel-web`, старый `lead-collector`, дополнительные workers или другие контейнеры этого проекта, останови и их с фактическими Compose-файлами. Ограничь внешний доступ на время обслуживания.

Пример дампа PostgreSQL; замени `YYYYMMDD-HHMM` на уникальную метку:

```text
docker compose exec -T db pg_dump -U tender_search -d tender_search -Fc -f /tmp/before-update-YYYYMMDD-HHMM.dump
docker compose cp db:/tmp/before-update-YYYYMMDD-HHMM.dump data/backups/before-update-YYYYMMDD-HHMM.dump
docker compose exec -T db pg_restore -l /tmp/before-update-YYYYMMDD-HHMM.dump
```

Создание файла внутри контейнера с последующим `compose cp` избегает повреждения бинарного дампа перенаправлением PowerShell. Проверка `pg_restore -l` подтверждает читаемость оглавления; полноценную проверку восстановления выполняй на отдельной БД.

Архив тома документов для той же точки остановки:

```text
docker compose run --rm --no-deps -v ./data/backups:/backup web tar -czf /backup/documents-YYYYMMDD-HHMM.tar.gz -C /app/data .
```

На Linux каталог резервных копий должен быть доступен пользователю контейнера (UID 10001); настрой точечные права, не делай каталог общедоступным. Если архив создать не удалось, не считай резервирование завершённым.

Отдельно сохрани `.env` и используемые локальные overrides в защищённом хранилище. Рассчитай контрольные суммы архивов и запиши установленный коммит. Не смешивай файл на хосте `data/first-login.txt` с Docker-томом `/app/data`: это разные хранилища.

## 9. Обновление существующей установки из main

1. Проверь правильный каталог, `origin`, ветку `main`, имя Compose-проекта, локальные изменения и используемые overrides. При незакоммиченных изменениях сохрани их согласованным способом; не стирай и не прячь автоматически.
2. Запиши предыдущий коммит и сохрани старый образ под отдельным тегом для возможного отката.
3. Получи обновление и собери новый образ, пока прежние контейнеры ещё работают:

```text
git status --short
git rev-parse HEAD
git fetch origin main
git pull --ff-only origin main
docker compose build web
```

Если fast-forward невозможен, выясни расхождение. Не делай принудительный reset или push.

4. Останови процессы и сделай согласованную резервную копию по разделу 8.
5. Примени миграции новой версией образа:

```text
docker compose run --rm --no-deps initialize
```

6. Для перехода со старой версии, где ещё не заполнены поисковые поля миграции `0012`, выполни:

```text
docker compose run --rm --no-deps web python manage.py backfill_search_projection
```

Команда обрабатывает незаполненные поля из сохранённых ответов без повторной загрузки портала. Не запускай `--all` без отдельной причины. Для старой базы до появления признака аванса при необходимости есть `backfill_advance_flags`.

7. Пересоздай службы на новом образе с теми же Compose-файлами, проектом и томами:

```text
docker compose up -d --no-deps --wait web worker search-worker indexer detail-indexer collection-monitor medical-indexer telegram
docker compose exec -T web python manage.py check
docker compose exec -T web python manage.py showmigrations --plan
```

Если до обслуживания индексатор был поставлен на паузу именно для обновления, возобнови его: `docker compose exec -T web python manage.py index_procurements --resume`. Не отменяй намеренную паузу владельца.

В этой версии прежний сбор базы клиентов отключён. Если остался контейнер `lead-collector`, останови его отдельно. Не удаляй неизвестные orphan-контейнеры автоматически: среди них может быть действующий туннель.

## 10. Перенос прежних данных на другой сервер

Это отдельная операция от `git clone`. Не запускай полный набор служб с пустой БД, если требуется перенести существующую.

Порядок:

1. На источнике останови запись и сделай копии БД, документов и секретов по разделу 8.
2. На целевом сервере получи код, настрой правильный Compose-проект, окружение и собери образ.
3. Запусти только `db` и `redis`. Целевая БД должна быть пустой и предназначенной именно для переноса. При наличии в ней данных сначала остановись и согласуй дальнейшие действия.
4. Передай архивы защищённым способом и проверь контрольные суммы.
5. Восстанови БД; пример для пустой БД `tender_search`:

```text
docker compose cp data/backups/source.dump db:/tmp/source.dump
docker compose exec -T db pg_restore --exit-on-error --no-owner --no-privileges -U tender_search -d tender_search /tmp/source.dump
```

6. Восстанови документы в пустой целевой том:

```text
docker compose run --rm --no-deps -v ./data/backups:/backup:ro web tar -xzf /backup/documents-source.tar.gz -C /app/data
```

Используй реальные имена архивов. Не распаковывай поверх чужих документов. Проверь права UID 10001 и доступ приложения к файлам.

7. Выполни `initialize`, необходимые backfill-команды и запусти службы, как при обновлении.
8. Сравни количество пользователей, подборок, избранного и документов с источником. Проверь один скачанный документ и поиск от обычного пользователя.
9. Убедись, что старые фоновые процессы и старый Telegram-получатель не продолжают работать параллельно новой основной установке.

Сохранение прежнего `DJANGO_SECRET_KEY` позволяет не ломать подписанные данные и существующие сессии. Пароль БД на новом сервере должен соответствовать его PostgreSQL. Восстановление SQL-дампа не переносит автоматически `.env` и файлы документов.

Не переноси старую очередь Redis вслепую: она может содержать задания, уже выполненные или привязанные к прежнему процессу. После остановки/переноса проверь незавершённые поиски и состояния фоновых задач; при необходимости обрабатывай их штатными механизмами приложения. Сохраняющиеся в PostgreSQL аренды заданий могут задержать продолжение до истечения срока; не очищай их вручную без диагностики.

## 11. Проверка результата

```text
docker compose ps -a
docker compose exec -T web python manage.py check
docker compose exec -T web python manage.py migrate --check
docker compose exec -T worker celery -A tender_search.web inspect ping --timeout 10
docker compose logs --tail 50 web search-worker worker indexer detail-indexer collection-monitor medical-indexer
```

Просматривай журналы локально; перед передачей фрагментов исключи секреты и персональные данные. Не включай в отчёт токен из URL Telegram-запроса.

HTTP-проверка без сторонних утилит:

```text
docker compose exec -T web python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health/', timeout=10).status)"
```

Проверь в браузере:

- открывается страница входа, после входа — главная;
- название «Госзакупки» чёрное, favicon «ГЗ», лишней подписи в шапке нет;
- администратор видит `/administration/`, может создавать, редактировать и удалять пользователей с подтверждением;
- доступны ровно две роли: «Пользователь» и «Администратор»;
- обычный пользователь не видит управление пользователями и блок «База активных закупок», прямые запросы к административным страницам запрещены;
- поиск запускается и завершается, фильтры сохраняются; избранное и документы доступны своему владельцу;
- на внешнем домене нет ошибок CSRF, HTTPS и статических файлов.

Не удаляй реального пользователя ради проверки. Проверки изменения данных выполняй на отдельно созданной тестовой записи с понятным назначением.

Успешный `/health/` не доказывает, что первоначальный сбор завершён. Проверь `ProcurementIndex(pk=1)`: `pending`, `error`, `started_at`, `completed_at`, `heartbeat_at`, `paused`. Нормальная работа — движение курсора/heartbeat без стойкой ошибки. Завершённый текущий цикл: пустой `pending`, пустой `error`, `completed_at >= started_at`. Медицинские источники имеют отдельные состояния `MedicalIndex`.

Не обещай готовую базу сразу после запуска: первоначальное заполнение может занимать часы. Число загруженных строк само по себе не подтверждает завершение. Полный архив закупок не собирается.

## 12. Если что-то пошло не так

- `DisallowedHost`: проверь домен в фактическом окружении web; не ставь `*` вместо диагностики.
- Ошибка CSRF по HTTPS: проверь origin, forwarding-заголовки и применение override.
- Нет входа после установки: проверь успешность `initialize`; он не меняет пароль существующего администратора. Для согласованного сброса есть `docker compose exec web python manage.py changepassword admin`.
- Поиск зависает: проверь `search-worker`, Redis и очередь `interactive`.
- Не пополняется база: проверь indexer, паузу, heartbeat, сохранённую ошибку и доступность источника; не удаляй курсор, лоты или БД.
- После clone нет старых пользователей: Git не содержит рабочие данные. Проверь имя проекта/тома и необходимость восстановления копии.
- Сбой миграции: не запускай оставшиеся службы и не применяй `--fake` автоматически. Определи причину и сохрани дамп.

Для отката кода используй сохранённый коммит/образ только при совместимости схемы БД. После несовместимых миграций нужен согласованный откат БД и документов к резервной копии; это может потерять изменения после копирования, поэтому сначала останови запись и согласуй восстановление. Не называй простое переключение Git полноценным откатом данных.

## 13. Итоговый отчёт агенту требуется дать владельцу

- URL приложения и установленный SHA коммита.
- Имя Compose-проекта и каталог установки.
- Состояние web, обоих workers, indexer, detail-indexer, collection-monitor, medical-indexer, PostgreSQL и Redis.
- Результат миграций и основных проверок.
- Началась ли загрузка базы или завершён текущий обход.
- Подключён ли Telegram; без отправки самовольных уведомлений.
- Где находится файл первого входа и резервные копии — без их секретного содержимого.
- Что требует действий владельца: домен, сертификат, токен, перенос данных или устранение ошибки источника.
