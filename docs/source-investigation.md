# Результаты проверки zakup.gov.kz

Дата проверки: 27 октября 2026 года. Реализован адаптер публичных методов; авторизация через ЭЦП и сессия личного кабинета не использовались.

## Подтверждённые возможности

| Проверка | Результат |
| --- | --- |
| Поиск «телефон», «бумага», «кабель» | По две страницы, по пять лотов на каждой, без дублей в проверенной выборке |
| Сумма | total_price__gte=10000 и total_price__lte=100000: все пять результатов в диапазоне |
| Статус | status_id=9: все пять результатов соответствуют фильтру |
| Способ закупки | purchase_method_id=12: все пять результатов соответствуют фильтру |
| Окончание приёма | offer_end_date__gte и offer_end_date__lte: пять результатов в проверенном периоде |
| Заказчик | customer_id: совпадение заказчика во всех пяти результатах |
| Место поставки | delivery_address_id__in: совпадение адреса во всех пяти результатах |
| Номер лота | lot_number: найден один соответствующий лот |
| Сортировка | ordering=id и ordering=-id: порядок пяти ID соответствует направлению |
| Объявления | Карточки и подробные лоты трёх объявлений получены |
| Документы | Получены списки файлов трёх объявлений, в том числе технические спецификации |
| Загрузка и чтение | Один PDF на 18 страниц, около 122 КБ; извлечено более 60 тысяч символов |

Это проверка конкретных выборок, а не гарантия полноты и неизменности поведения источника. Встроенный q находит также «телефонный»; точное совпадение и несколько условий будут проверяться локально на этапе 3.

Проверенные объявления: внутренние ID 40901055, 40899512, 40899193. Документы доступны через general-files; поле lot сохраняет связь технической спецификации с конкретным лотом. Общие файлы имеют lot=null. Группы требований могут иметь files=null — это нормальный пустой список, а не ошибка.

## Адреса методов

Основной адрес: https://zakup.gov.kz

- GET /api/core/api/public/lots/
- GET /api/core/api/public/announcements/
- GET /api/core/api/public/announcements/{id}/
- GET /api/core/api/public/announcements/{id}/lots/
- GET /api/core/api/public/announcements/{id}/general-files/
- GET /api/core/api/dicts/lot-statuses/
- GET /api/core/api/dicts/purchase-methods/
- GET /api/core/api/dicts/systems/
- GET /api/core/api/dicts/katos/

Списки закупок возвращают results, count, next, previous. Справочники статусов, способов закупок и систем — массивы целиком. КАТО возвращает result в единственном числе и пагинацию; параметр limit работает для него, но небольшие справочники могут возвращаться полностью.

Идентификатор региона — внутренний id справочника КАТО; code — отдельный код классификатора. В испытании фильтра проверен конкретный адрес, включение всех дочерних адресов при выборе области ещё не подтверждено. В интерфейсе нельзя обещать такую иерархическую фильтрацию без отдельной проверки.

Ссылки на публичные карточки формируются как /announcement/{announcement_id}#lot-{lot_id}. Внутренние ID, external_id и печатные номера сохраняются отдельно.

## Пагинация и изменения данных

Использовать next источника, проверяя домен и путь. Клиент ограничивает число страниц, не делает лишнего запроса после последней разрешённой страницы и сохраняет признак наличия продолжения. При обходе сохранять выбранную сортировку.

Во фронтенде найден предел окна 10 000 записей; это учтено как ограничение клиента. Точная граница серверного окна массовой загрузкой не проверялась. Разбивка на периоды и устранение дублей нужны для будущего мониторинга: записи могут добавляться между запросами, а offset не обеспечивает неизменный снимок реестра. Отслеживание всех обновлений только по возрастанию ID не гарантируется.

## Даты и документы

В списках даты представлены ISO 8601 с часовым поясом, в карточках встречаются Unix seconds. Клиент приводит оба варианта к UTC. Даты без часового пояса отклоняются, чтобы не подставлять предположение незаметно.

Ссылки на файлы в проверенных ответах размещены на v3bl.goszakup.gov.kz. Скачивание ограничено разрешёнными HTTPS-хостами, размером и проверкой непубличных адресов; каждое перенаправление проверяется заново. Имя локального файла формируется по SHA-256. Исходные имена и данные документов не используются как команды.

Наличие ссылки не гарантирует скачивание каждого файла. Запрос документов и успешная загрузка одного файла не подтверждают полноту документации по всем площадкам и способам закупок. Поддержку других файловых хостов расширять после отдельной проверки. Потоковое ограничение размера действует и при отсутствии Content-Length.

## Ошибки и устойчивость

Для JSON-запросов реализованы тайм-ауты и до трёх попыток при сетевых ошибках, 429 и 5xx. Учитывается Retry-After; при запросе ожидания больше минуты операция завершается понятной ошибкой для последующего планирования. 401/403 не обходятся. Неожиданная схема и HTML вместо JSON — отдельные ошибки, а не пустые результаты.

Начальный ограничитель — один запрос в секунду на экземпляр синхронного клиента. Глобальный лимит между несколькими workers, изоляция PDF-парсинга и восстановление заданий относятся к следующим этапам. Официальные квоты публичных методов не установлены этим исследованием.

## Проверки и воспроизведение

Тесты находятся в tests/test_client.py; живой сценарий — scripts/probe_source.py. Отчёт каждого запуска сохраняется в data/probe/report.json. Примеры реальных исходных ответов имеются в корне проекта; новые скачанные файлы и окружение исключены из Git.

Автоматические тесты покрывают пагинацию и её циклы, недоверенные ссылки, ограниченные повторы, запрет доступа, изменение схемы, пустые группы документов, обе формы справочников, даты, хосты файлов, размер и очистку частично загруженного файла.

## Выбор обработки документов

Перед этапом 4 сравнить Microsoft MarkItDown и pypdf. Проверить одинаковый набор русских и казахских PDF/DOCX: текст, таблицы, порядок чтения, переносы, цифры, маркировки, скорость, память и привязку к страницам. Отдельно оценить сканы, требующие OCR. Сейчас pypdf используется только для проверки чтения одного текстового PDF; окончательный выбор обработчика документов не сделан.
