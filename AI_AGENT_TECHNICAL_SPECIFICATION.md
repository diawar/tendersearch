Описание очереди, повторов и ограничений в [README](README.md#раздельное-обновление-реестров-и-подробностей) имеет приоритет над старым описанием синхронного обхода ниже. При обновлении обязательно запускайте `detail-indexer` вместе с `indexer`.

### Общая база и локальный поиск — актуальное поведение

- `core/index_service.py`: один фоновый сборщик загружает все способы закупки, статусы источника 6/7/9 с неистёкшим сроком подачи, включая закупки до начала приёма. Архив и остальные статусы не покрываются полностью. Выбранные пользователем способы и статусы применяются при локальном поиске, не ограничивая общий сбор.
- Форма больше не содержит глубины. Новые задания `web_search` ищут по всему накопленному индексу, без сетевого обхода на каждое слово. Сохранённые условия и исключения сохранены; старые поля глубины игнорируются. Логика И/ИЛИ, совпадения и исключений прежняя.
- `IndexedLot` хранит публичную строку и дополнительные описания своего лота из `plan_items`. Это не OCR и не поиск в файлах. Подробные карточки объявлений переиспользуются между пользователями; для общего сборщика срок кэша — 24 часа (старый конвейер — 6 часов).
- `ProcurementIndex` хранит курсор, окна сроков, время обхода, ошибку, паузу и аренду. При количестве более 9000 окно делится по сроку подачи, чтобы обойти предел API 10000. Страницы идут с перекрытием, уникальность по ID. Курсор фиксируется после обработки всей страницы; при сетевой ошибке основного обхода повторяется страница. Если API успешно вернул карточку без нужного лота, сохраняется базовая строка с `_details_pending=True`, а сбор остальных продолжается. После каждой страницы повторно проверяется не более одного такого лота, ожидающего более 15 минут; последующие полные обходы также проверяют их. Число ожидающих показано в интерфейсе. Пока есть активные непроверенные описания, `ready=False` и новое время полного обхода не фиксируется. Истёкшие/неактивные лоты не блокируют готовность.
- Сбор выполняется круглосуточно с общим ограничителем запросов Redis. Расписание 07:00–19:00 относится только к проверкам и рассылкам подборок. После полного обхода следующий начинается через 15 минут; это интервал до запуска, не гарантия обновления всей базы за 15 минут. Начальный сбор может занимать часы; ночью загрузка не останавливается. Отдельного потока мгновенного поступления новых лотов пока нет.
- Записи с истёкшим сроком сразу исключаются из новых локальных поисков. После полного обхода исчезнувшие из активного списка помечаются `current=False`. Физическое удаление старых записей пока не включено. Избранное, история и ранее сохранённые результаты остаются; документы удаляются по прежнему правилу последнего избранного пользователя.
- Панель `/search/index-status/` обновляется каждые 15 секунд: число загруженных лотов, приблизительное количество из последней оценки источника, состояние и время полного обхода. Свежесть полного обхода — 6 часов. Это обход изменяющегося списка, а не атомарный снимок портала; до завершения результат явно неполный. Даже после обхода сведения могут отставать, включая дополнительные описания из суточного кэша.
- Для выбора архивных/неподдерживаемых статусов результат помечается неполным. Это не доказательство отсутствия закупок на портале. Локальный поиск фильтрует сумму, срок, БИН, регион/город, номер, способ и статус, затем проверяет слова и исключения. Бизнес-дедупликация сохранена.
- Ручные поиски обслуживаются отдельным `search-worker`, очередь `interactive`. Основной `worker`, очередь `celery`, выполняет мониторинг, документы и обновления карточек. `indexer` — отдельная команда `index_procurements`, не блокирующая очереди Celery.
- Рассылки подборок используют тот же локальный индекс и ждут первого полного свежего обхода. `SearchProfile.index_baseline_at` задаёт новую начальную точку: накопленные результаты отмечаются просмотренными без отправки. Затем отправляются только ранее не встречавшиеся объявления с датой публикации не раньше этой точки. Задним числом догруженные старые объявления не рассылаются. Статусные уведомления и ручные действия сохраняют отдельные правила круглосуточной отправки.
- Миграция `0007_shared_procurement_index` создаёт две таблицы и начальную точку подборок; переносит уже известные активные строки, только если дополнительные описания ранее проверены. Не удаляет пользователей, подборки или избранное.
- Старый `execute_search` оставлен для совместимости и регрессионных тестов. Производственные ручные поиски и подборки используют `execute_local_search` (`USE_LOCAL_INDEX=True`). Отключение флага влияет только на подборки, это не полный механизм отката.

Обновление контейнеров: собрать `web`, выполнить `initialize` (миграции), затем пересоздать `web`, `tunnel-web` при наличии туннеля, `worker`, `search-worker`, `indexer`, `telegram`. Для остановки/продолжения загрузки: `docker compose exec web python manage.py index_procurements --pause` / `--resume`. Пауза сохраняет курсор. После аварийного завершения аренда сборщика истекает через 30 минут.

Проверки нового конвейера: `core/test_index.py` — поиск без сети и глубины, фильтры, неполная/устаревшая база, отмена, повтор страницы, разбиение большого окна, проверка ответа источника, взаимное исключение сборщиков и отсутствие архивной рассылки.

## 2. Назначение и границы продукта

GoszakupOver помогает поставщику находить закупки Казахстана, изучать условия, сохранять лоты и получать персональные Telegram-уведомления.

Реализованы поиск, персональные подборки, избранное, скачивание документов, мониторинг новых объявлений и отслеживание статуса отдельных объявлений.

В границы текущего продукта не входят:

- автоматическая подача заявок;
- подписание ЭЦП и управление NCALayer;
- заключение договоров, оплата и исполнение закупки;
- автоматическое определение права пользователя участвовать в конкретной закупке;
- подтверждённый полный охват всех площадок Казахстана;
- гарантированное совпадение выдачи с платным агрегатором.

Рабочая интеграция читает публичные данные `zakup.gov.kz`. Вход через NCALayer на государственный портал приложению для текущих публичных GET-запросов не нужен.

## 3. Термины и единицы учёта

| Термин | Смысл в проекте |
| --- | --- |
| Объявление | Процедура закупки, содержащая один или несколько лотов |
| Лот | Основная строка поисковой выдачи и объект добавления в избранное |
| Объединённый лот | Один исходный лот с несколькими вложенными пунктами плана |
| Пункт плана | Вложенная позиция; не всегда самостоятельный лот |
| Подборка / профиль | Сохранённые персональные условия поиска и настройки мониторинга |
| Запуск поиска | `WebSearch` с неизменяемой спецификацией конкретного запуска |
| Дополнительное описание | Структурированный текст `plan_items[].extra_description*`, получаемый через API без чтения PDF |
| Поиск по документации | Поиск внутри скачанных файлов; отдельная, ещё не внедрённая функция |
| Глубина | Ограничение числа исходных записей, а не количество HTTP-запросов и не гарантированное число совпадений |
| Активность | В новых группах — сочетание исходного статуса и сроков, а не одно слово «Опубликован» |

Один лот не должен повторяться из-за нескольких ключевых слов или двух проходов поиска. Разные лоты одного объявления могут быть отдельными строками. Telegram-рассылка новых закупок объединяет такие строки на уровне объявления.

## 5. Техническая архитектура

### 5.1. Стек

| Компонент | Реализация |
| --- | --- |
| Язык | Python 3.11+, контейнер Python 3.12 |
| Backend | Django `>=5.2,<5.3` |
| UI | Django Templates, локальные CSS и JavaScript, HTMX 2.0.11 |
| Иконки | Локальный SVG-спрайт Lucide с лицензией |
| БД | PostgreSQL 17 |
| Фоновые задания | Celery `>=5.5,<6` |
| Брокер и ограничитель запросов | Redis 7 |
| HTTP | HTTPX `>=0.28,<0.29` |
| WSGI | Gunicorn, один процесс, два потока |
| Статика | WhiteNoise с manifest-хешированием |
| Запуск | Docker Compose |
| Тестовая БД | SQLite только при `TENDER_SQLITE=1` |

`pypdf` входит в дополнительные зависимости разработки. MarkItDown, Tesseract и полноценный конвейер обработки файлов в рабочий образ не подключены. Не считать их установленными только на основании раннего ТЗ.

### 5.2. Службы Compose

| Служба | Назначение |
| --- | --- |
| `db` | PostgreSQL |
| `redis` | Брокер, результаты Celery и общий rate limit |
| `initialize` | Миграции и первичное создание администратора; нормально завершается после выполнения |
| `web` | Локальный интерфейс `127.0.0.1:8000` |
| `worker` | Celery, `--concurrency=1`, `--max-tasks-per-child=50` |
| `telegram` | Long polling Telegram, планирование и доставка уведомлений |
| `tunnel-web` | Дополнительный HTTPS-интерфейс из `compose.tunnel.yaml` |

Именованные тома: `database`, `documents`, `queue`. Общий том документов смонтирован в приложения как `/app/data`; `MEDIA_ROOT=/app/data/documents`.

**Важно:** локальная папка проекта `data/` и `/app/data` в именованном томе Docker — разные хранилища. Исследовательский JSON на компьютере не появляется автоматически внутри контейнера и наоборот.

Проект запускается из корня клонированного репозитория. Переносимость приложения не должна зависеть от имени пользователя или абсолютного пути на исходной машине.

### 5.3. Часовые пояса

- Хранение дат: timezone-aware, нормализация в UTC.
- Django: `Asia/Qyzylorda`.
- Правила расписания Telegram: явно `Asia/Almaty`.
- На текущем этапе обе зоны имеют UTC+5, но в коде использовать имена зон, а не арифметику с фиксированным смещением.
- Источник возвращает и ISO 8601, и Unix timestamp; преобразование выполняет `utc_datetime()`.

## 6. Пользователи и доступ

1. Самостоятельная регистрация отсутствует.
2. В исходной установке созданы администратор и обычные тестовые пользователи. Учётные записи находятся в базе, не в репозитории; пароли в ТЗ не включать.
3. Поисковые запуски, подборки, избранное, подписка и отслеживание принадлежат пользователю.
4. Чужой запуск или чужой профиль нельзя получить подстановкой ID.
5. Данные публичных лотов, объявлений и общий кэш могут использоваться совместно.
6. Локальный файл документа выдаётся только пользователю, у которого соответствующий лот находится в избранном, с проверкой принадлежности документа лоту/объявлению.
7. `/admin/` и вложенные адреса сейчас возвращают 403 для всех, включая администратора. Управление пользователями реализовано отдельно по адресу `/administration/` для роли «Администратор».
8. В `/administration/` доступны создание, редактирование, смена пароля и роли, удаление с подтверждением. Роли: «Пользователь» и «Администратор». Пароли хешируются средствами Django. Учётную запись `admin` нельзя удалить, переименовать, отключить или понизить в роли.

Раздел «Администрирование» виден и доступен всем активным пользователям с ролью «Администратор»; содержит список пользователей, добавление, редактирование с выбором роли и удаление с подтверждением. Блок «База активных закупок» доступен по тому же правилу.
- Убраны декоративные подписи «РАБОЧЕЕ ПРОСТРАНСТВО», «ЗАКУПКИ КАЗАХСТАНА» и соответствующий слоган.
- Заголовок формы входа — просто «Вход».
- Не прикладывать скриншот после каждой небольшой доработки: владелец прямо отказался от этого.

### 7.2. Главная

Две карточки показателей:

1. «Подборки»: всего / отслеживается.
2. «Избранное»: всего / отслеживается по статусу.

Пример отображения: `3 / 3`. Блок количества новых уведомлений удалён.

### 7.3. Форма поиска

Над формой — «Мои подборки». В строке ключевых слов находятся поле тегов, «Поиск», «Сохранить» и сброс. Необязательное поле имени подборки удалено.

Форма компактная. Ранее добавленная кнопка «Скрыть фильтры / Показать фильтры» удалена по указанию владельца; текущие фильтры постоянно доступны.

Цветовая система:

- ключевые слова и условия объединения/совпадения — синие;
- условия закупки, сроки и номера — зелёные;
- исключения — красные;
- никаких разноцветных случайных тегов.

Заголовок «КЛЮЧЕВЫЕ СЛОВА» оформлен как заголовки разделов фильтров и выделен синим.

### 7.4. Выпадающие списки

- Статус, способ, область и город поддерживают множественный выбор.
- Область называется «Область поставки»; рядом находится «Город».
- Город связан с областью по КАТО.
- В статусах и способах есть группы с раскрываемыми вложенными пунктами.
- Чекбокс группы выбирает/снимает все дочерние пункты; при частичном выборе используется промежуточное состояние.
- Список закрывается при клике снаружи, уходе фокуса или Escape.
- Под списком полностью выбранная группа показывается одним тегом с названием группы; при частичном выборе показываются только выбранные дочерние пункты. Крестик группы снимает все её значения, крестик пункта — только этот пункт. Это же правило применяется в «Выбранных условиях». В форме и сохранённых подборках остаются конкретные исходные ID.
- Для обычных одиночных select — объединения, совпадения, вида номера и глубины — отдельные подписи выбранных значений под полем не выводятся.

### 7.5. «Выбранные условия»

Блок находится после формы, существует и до запуска, и на странице результатов. Отражает текущие изменения формы.

Порядок: ключевые слова → условия закупки → сроки и номер → исключения. По требованию от 29.10.2026 «Объединение условий», «Совпадение» и «Глубина поиска на слово» в этой строке не показываются; поля формы, их сохранение и влияние на поиск сохраняются.

Ключевые слова и положительные условия имеют знак `+`, исключения — `−`. Снимаемые условия удаляются крестиком.

Справа — квадратная синяя кнопка поиска без текста. Во время поиска она становится красной кнопкой отмены с крестиком, после завершения/отмены возвращается к лупе.

### 7.6. Результаты

- Переключение таблица/карточки; предпочтение сохраняется в сессии.
- Пагинация по 25 строк.
- Сортировка: `announcement_publish_date` по убыванию, затем `source_id` по убыванию; отсутствующая дата в конце.
- Основные столбцы: «Лот и заказчик», «Сумма, ₸», «Даты заявки», «Статус».
- В «Даты заявки» первая строка — начало, вторая — окончание. Не создавать два отдельных столбца.
- Звезда и самолётик находятся в первом столбце. Отдельного последнего столбца действий нет.
- Совпавшие слова подсвечиваются в наименовании; найденные условия перечисляются в строке.
- Во время ожидания показываются вращающееся кольцо, состояние поиска и количество проверенных записей. Верхняя кнопка поиска отключена.
- Пустая выдача, ошибка, отмена и неполная выдача различаются.
- Текст о полной проверке полученной выдачи находится мелким шрифтом в верхнем блоке количества. Он не является заявлением о проверке всего портала.

### 7.7. Карточка

Показываются сведения лота и объявления, заказчик, сумма, сроки, описание, статус, место поставки, документы и ссылка на первоисточник. Статусы оформлены тем же бейджем, что в избранном.

Ссылка возврата сейчас всегда ведёт в `/favorites/` и подписана «← В избранное».

Карточка автоматически обновляется при первом открытии и после устаревания более пяти минут; есть ручное обновление. При ошибке не затирать прежние сведения пустыми значениями.

### 7.8. Избранное

- Таблица в том же стиле, что результаты.
- Дополнительный столбец «Дата добавления».
- Сортировка по сумме, дате добавления и статусу, с переключением направления по заголовку.
- По умолчанию недавно добавленные сверху.
- Сортировка сохраняется в ссылках пагинации.
- Удаление выполняется жёлтой звездой, не крестиком.
- Счётчик меню обновляется и при действиях из поиска; используются HTMX OOB-фрагменты.

## 8. Правила тегов и сопоставления текста

1. Один тег — одно слово, не фраза. Количество тегов программно не ограничено; длина одного слова — не более 150 символов.
2. Разделители: пробелы, запятые, точка с запятой. Enter также фиксирует ввод.
3. Уход фокуса из поля фиксирует незавершённое слово.
4. При наведении появляется карандаш; редактирование подтверждается пробелом, Enter или уходом фокуса. Escape отменяет редактирование.
5. Одинаковые теги не размножаются.
6. По умолчанию включено ИЛИ. И требует все слова внутри одного лота, объединяя доступное название и описание, включая дополнительные описания его пунктов плана.
7. Нормализация: Unicode NFC, сворачивание пробелов, `casefold`. Слова пользователя не интерпретируются как регулярные выражения.
8. Морфология, автоматическая замена `ё/е`, транслитерация и неявные синонимы не реализованы.

| Режим | Реализованная семантика |
| --- | --- |
| Содержит текст | Поиск подстроки |
| Целые слова | Границы слова через экранированное регулярное выражение |
| Точная фраза | В matching-модуле поддерживается последовательность с границами; UI новых тегов разбивает фразы на слова, полноценный ввод многословной фразы отдельно не реализован |
| Название целиком | Сравнение нормализованного названия целиком; расширенный обход не выполняется |

**Исключения всегда проверяются как подстроки**, независимо от режима включающих слов. `услуг` исключает `услуги`, `ремонт` — `ремонта`.

Известная особенность подстрок: `мыш` совпадает с `мышц`, `внутримышечного` и другими посторонними словами. Это следствие выбранного режима, а не доказательство релевантности закупки компьютерных мышей. Нельзя скрыто изменить эту семантику для всех пользователей.

### 10.1. Статусы

Новые поиски по умолчанию выбирают `open:6`, `open:7`, `open:9` — группу «Приём открыт».

- `open:<id>`: исходный статус совпадает, окончание позже момента начала поиска, начало уже наступило.

## 11. Фактический алгоритм поиска

Рабочие модули: `matching.py`, `core/forms.py`, `core/search_service.py`, `core/source.py`, `client.py`.

1. Создать `WebSearch`, проверить ограничение активных запусков пользователя, отправить задачу Celery.
2. Атомарно перевести `queued → running`. Повторная доставка задачи не должна повторно выполнять уже начатый/законченный поиск.
3. Разрешить БИН заказчика, подготовить фильтры и вычислить временные условия на момент запуска.
4. Для каждого ключевого слова запросить обычную выдачу `q=<слово>` с сортировкой `-publish_date`.
5. Если включены дополнительные описания и режим не «Название целиком», выполнить ещё один общий проход по последним кандидатам с теми же фильтрами, без ограничения `q` ключевым словом.
6. Размер страницы обычного текущего обхода — 50; число страниц — `ceil(depth / 50)`.
7. Проверить локальные условия статуса/дат. Не тратить запрос расширенной карточки на уже отклонённый по срокам лот.
8. Получить лоты объявления через `announcements/{internal_id}/lots/`, используя общий кэш.
9. Выбрать подробный объект **именно текущего лота по внутреннему ID**.
10. Объединить краткие описания с дополнительными описаниями пунктов плана текущего лота: `extra_description_ru`, `extra_description_kk`, `extra_description`.
11. Проверить И/ИЛИ, режим совпадения и исключения локально.
12. Сохранить подходящий лот и `SearchHit`; обновлять прогресс по страницам.
13. Завершить поиск как полный, неполный, ошибочный или отменённый.

Текст другого лота того же объявления не должен автоматически давать совпадение текущему. В объединённом лоте проверяются его собственные вложенные пункты плана.

`AnnouncementLotCache` хранит подробные лоты объявления на шесть часов; в одном запуске есть дополнительный словарь в памяти. Если нужного лота нет в сохранённой карточке, выполняется повторный запрос. Автоматическое удаление старых строк кэша ещё не реализовано.

Название объявления пока **не включено** в локальное сопоставление наравне с названием/описанием лота. Это одно из отличий от Tenderbot.

### 11.1. Что ограничивает глубина

Глубина применяется к каждой обычной выдаче слова и отдельно к одному общему проходу кандидатов для дополнительных описаний. Это не глобальный лимит всех строк запуска.

Например, на глубине 1100 может быть проверено 1115 исходных записей: 1100 общих кандидатов плюс 15 результатов обычных запросов слов. Счётчик может учитывать встреченные повторно исходные строки; он не равен числу уникальных лотов и не равен числу HTTP-запросов.

Для старых спецификаций поддерживается `auto_pages`: до 100 страниц по 100 записей в пределах окна источника 10 000. Новая форма использует явную глубину, а не этот режим.

### 11.2. Полнота и состояния

Состояния `WebSearch`: `queued`, `running`, `done`, `partial`, `error`, `cancelled`.

`complete=True` допускается только если все проходы исчерпали полученную выдачу. Если есть `next`, выбранной глубины недостаточно и результат неполный даже без сетевой ошибки.

Прерывание источника сохраняет уже найденные совпадения. Ошибка не должна превращаться в успешный пустой результат.

В интерфейсе допускается не более двух активных поисков пользователя за проверяемое 25-минутное окно. Устаревший запуск при обращении к результатам переводится в `partial` либо `error` с объяснением.

### 11.3. Отмена

Отмена — отдельный POST только владельца запуска. Она атомарно меняет статус, сохраняет найденные результаты и снимает режим ожидания в UI.

Фоновое исполнение проверяет состояние перед проходами, при обработке страниц и перед запросами дополнительных сведений. Текущий сетевой запрос может завершиться; насильственное уничтожение процесса не используется. Финальное обновление задачи не должно перезаписать `cancelled`.

### 11.4. Дедупликация

- В рамках запуска исключаются повторные внутренние ID.
- Если присутствуют номер лота, номер объявления и БИН заказчиков, используется бизнес-ключ из этих значений.
- Если данных для бизнес-ключа недостаточно, применяется исходный ID.
- На уровне БД действует уникальность `(search, lot)`.
- Удалять строки только из-за одинакового названия, суммы или общего объявления нельзя.
- `Lot` уникален по `(announcement, source_id)`; `Announcement` — по `(source, source_id)`.

## 12. Подборки и история

1. Сохраняются все отборы, ключевые слова, исключения, режимы, глубина, статусы и способы, а не только текст тегов.
2. Данные исходной формы находятся в `SearchProfile.filters['form']`; нормализованная спецификация — в `filters['specification']`.
3. Имя генерируется по ключевым словам с разделителем ` · `.
4. После сохранения неизменённых условий «Сохранить» недоступна. Изменение условия включает кнопку; возврат к сохранённому состоянию снова отключает.
5. Само нажатие «Поиск» не считается изменением профиля.
6. Выбор подборки восстанавливает весь её набор условий.
7. Изменение сохранённых условий сбрасывает базовую выдачу мониторинга и отменяет ожидающие уведомления старых условий.
8. На странице поиска показываются семь последних пользовательских запусков компактным списком. Служебные обходы мониторинга исключаются из этого списка.
9. Подборки персональны; изменение/удаление чужой подборки запрещено.

## 13. Избранное, самолётик и документы

### 13.1. Матрица действий

| Действие | Избранное | Слежение за статусом | Документы |
| --- | --- | --- | --- |
| Нажать серую звезду | Добавить | Не включать | Поставить загрузку в очередь |
| Нажать серый самолётик | Добавить автоматически | Включить при подключённом Telegram | Поставить загрузку в очередь |
| Нажать синий самолётик | Оставить | Выключить, отправить подтверждение | Оставить, пока лот в избранном |
| Нажать жёлтую звезду | Удалить | Выключить, отменить старые отправки, сформировать подтверждение выключения | Удалить ненужные копии |

В поиске, карточке и избранном используются одни и те же цвета: невыбранная звезда серая, выбранная жёлтая; выключенный самолётик серый, включённый синий.

Слежение хранится на уровне объявления и пользователя, а избранное — на уровне лота. Сейчас удаление избранного лота отменяет слежение владельца за всем соответствующим объявлением, даже если у него есть другой избранный лот этого объявления. Не менять это поведение незаметно.

### 13.2. Загрузка

- Сигнал создания `Favorite` после фиксации транзакции ставит фоновую задачу.
- Загружаются общие документы объявления и документы выбранного лота. Файлы других лотов не скачиваются для него автоматически.
- Контрольная сумма SHA-256 определяет безопасное локальное имя; исходное имя используется при скачивании пользователем.
- Повторное добавление не должно повторно скачивать уже сохранённую существующую копию.
- В карточке отображаются очередь/загрузка, список файлов, ошибки и возможность повторить неудачную загрузку.
- Ошибка одного файла не должна уничтожать успешно сохранённые остальные.
- Восстановление загрузки, застрявшей более чем на 25 минут, доступно через повторную попытку после обновления состояния.

Состояния `LotDocumentDownload`: `queued`, `running`, `done`, `partial`, `error`, `cancelled`. У отдельных документов используются `pending`, `downloading`, `ready`, `error`.

### 13.3. Удаление и общие копии

После удаления избранного запускается очистка. Документ лота нужен, пока соответствующий лот остаётся в избранном хотя бы у одного пользователя; общий документ объявления — пока остаётся хотя бы один избранный лот этого объявления.

Удаление записи и физическое удаление файла согласуются через транзакцию и `on_commit`. Перед удалением физической копии проверяется, что другие версии документов не ссылаются на тот же путь. Доступ бывшего владельца избранного к локальному скачиванию прекращается независимо от сохранения общей копии другим пользователям.

### 13.4. Ограничения текущей реализации

- Рабочий процесс не извлекает и не индексирует текст файлов.
- Сохранённый файл обычно переиспользуется без повторного скачивания для проверки изменения содержимого. Постоянное обнаружение новой версии файла ещё не построено.
- Нет полноценного пользовательского интерфейса версий и истории изменений документа.
- Ошибки удаления файла сейчас могут перехватываться без полноценной панели диагностики; очистку нужно сделать наблюдаемой на следующем этапе.

## 14. Telegram

### 14.1. Подключение

Бот: `@tender_over_bot`. Настройки: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` в локальном `.env`.

Пользователь нажимает подключение в настройках, получает deep link с одноразовым случайным токеном и нажимает Start в личном чате. В БД сохраняется только SHA-256 токена привязки. Срок — десять минут. Повторное использование, истёкший токен, групповой чат и привязка уже занятого chat ID отклоняются.

Webhook не требуется: команда `telegram_monitor` использует long polling и сохраняет offset в `TelegramCursor`. Одновременно запускать несколько получателей обновлений одного бота нельзя.

Команда `/stop` выключает подписку. Отключение через веб-настройки дополнительно выключает подборки и статусные задания и отменяет ожидающие доставки.

### 14.2. Два разных временных правила

| Тип события | Ограничение |
| --- | --- |
| Проверки сохранённых подборок и рассылка новых закупок | Ежедневно с 07:00 включительно до 19:00 исключительно, `Asia/Almaty` |
| Включение/выключение слежения отдельного объявления | Без ограничения по времени суток |
| Доставка сообщения об изменении статуса | Без ограничения по времени суток |

Нельзя снова распространить дневное окно на статусные уведомления: владелец явно отменил это ограничение для них.

Текст в настройках: «Проверки — ежедневно с 07:00 до 19:00 по Алматы». Это описание проверок подборок.

### 14.3. Мониторинг подборки

- Самолётик рядом с подборкой включает/выключает её мониторинг; по умолчанию выключен.
- Интервал — целые часы `1..12`; только кнопки вверх/вниз. Нельзя вводить текст, дроби, вставлять значение или получать текстовый курсор в поле.
- Раннее требование про шаг 0,5 часа заменено более поздним требованием целых значений 1–12.
- Данные в БД хранятся в минутах, UI показывает часы.
- Первая успешная проверка создаёт baseline без рассылки старых закупок.
- Если новых объявлений нет, бот ничего не пишет. Сообщений «новых не появилось» быть не должно.
- Далее отправляются только впервые обнаруженные объявления.
- Дедупликация действует на пользователя и объявление, в том числе между несколькими подборками.
- Текущий ключ объявления строится из доступного идентификатора системы и номера, иначе — исходного ID; сохраняется его SHA-256.
- В одном уведомлении показывается один найденный лот объявления.
- Название подборки должно быть в начале уведомления, а не скрыто внизу.
- Сетевой сбой не считается успешным пустым baseline.
- Ожидание Redis также проверяет дневное окно до и после ожидания; запрос не должен начаться после его закрытия.

### 14.4. Слежение за статусом

- Включение создаёт `AnnouncementWatch` с новым поколением и исходной проверкой.
- Авторитетный статус берётся из **карточки объявления**, а не из статуса строки лота поискового индекса.
- После первой успешной проверки отправляется «Слежение включено» с номером, названием, текущим статусом и ссылкой.
- Далее проверка запланирована ежедневно на 07:00 следующего дня по Алматы. Если исполнение задержалось, проверка/отправка не блокируются дневным окном.
- Смена статуса отправляет прежний и новый статус, дату и ссылку.
- Неизменный статус не порождает сообщение.
- После ошибки исходное состояние не затирается; повтор откладывается примерно на час.
- Выключение отправляет «Слежение отключено» с названием, номером и ссылкой.
- После выключения обычные ожидающие события отменяются; событие выключения разрешено отправить при выключенном watch и удалённом избранном.
- Новое поколение слежения не должно получить устаревшее событие предыдущего включения.

Подтверждение включения зависит от успешной проверки и очереди. Круглосуточная доставка не означает мгновенное обнаружение смены статуса: проверка по-прежнему раз в день.

### 14.5. Формат и надёжность доставки

Сообщения используют Telegram HTML с экранированием значений, читаемые заголовки, номер, название, сумму/заказчика/сроки по типу сообщения и inline-кнопку перехода на госзакуп.

Состояния доставки: `pending`, `sending`, `sent`, `cancelled`, `error`, `uncertain`. Атомарный захват защищает от двойной отправки. При 429 учитывается `retry_after`; при 403 отключается подписка. При неизвестном исходе сетевой отправки автоматическое повторение отключено, чтобы не создавать дубли.

Не обещать строгое exactly-once: при неопределённом сетевом исходе сообщение может остаться неподтверждённым. Не выводить URL Telegram с токеном в HTTPX-логи или исключения.

## 15. Внешние источники и ограничения адаптеров

### 15.1. Рабочий публичный API

Базовый адрес: `https://zakup.gov.kz`.

| GET-метод | Использование |
| --- | --- |
| `/api/core/api/public/lots/` | Кандидаты и обычный поиск |
| `/api/core/api/public/announcements/{id}/` | Авторитетная карточка объявления |
| `/api/core/api/public/announcements/{id}/lots/` | Подробные лоты и дополнительные описания |
| `/api/core/api/public/announcements/{id}/general-files/` | Общие и привязанные к лоту документы |
| `/api/core/api/public/organizations/` | Разрешение БИН заказчика |
| `/api/core/api/dicts/lot-statuses/` | Статусы |
| `/api/core/api/dicts/purchase-methods/` | Способы |
| `/api/core/api/dicts/katos/` | География |

В клиенте также есть доступ к реестрам `announcements`, `plan-items` и некоторым справочникам. Отдельный пользовательский поиск по реестру объявлений, протоколам, договорам и победителям не построен.

Формат списков: `count`, `next`, `results`. `limit <= 100`, окно `offset + limit <= 10000`. Множественные ID передаются через `__` в проверенных фильтрах `...__in`.

Не считать произвольный параметр поддержанным по HTTP 200: источник может его проигнорировать. Например, пробный `lot_number__in` вернул огромную несвязанную выдачу и **не должен использоваться как подтверждённый массовый фильтр**.

Критические эмпирические ограничения:

1. `q` не обеспечивает поиск по `extra_description*`.
2. В проверенном лоте «Манипулятор \"мышь\"» запрос по номеру находил запись; добавление `q=мыш` или `q=мышь` давало ноль, а `q=манипулятор` находило. Нельзя считать выдачу `q` полным множеством совпадений в отображаемых полях.
3. Поиск по номеру объявления подтверждён прямыми проверками.
4. `plan-items/{id}/` при исследовании возвращал 404; не считать этот адрес рабочим только по REST-аналогии.
5. Поле `status.is_active` и подпись «Опубликован» сами по себе не доказывают, что срок не истёк.
6. Внутренние ID новой платформы, `external_id`, печатные номера и ID пунктов плана различаются.

### 15.2. Ограничитель и HTTP

- Общий RedisGate резервирует примерно один запрос в секунду между процессами.
- При недоступном Redis обращения прекращаются с ошибкой; обходить ограничитель нельзя.
- Перегруженная очередь резервирования также даёт ошибку, а не неограниченные параллельные запросы.
- HTTP-клиент использует тайм-аут около 30 секунд, connect около 10 секунд, до трёх попыток для предусмотренных сетевых ошибок, 429 и 5xx.
- 401/403 не обходятся; невалидная схема — ошибка, а не пустая выдача.
- Для файлов: HTTPS, разрешённые хосты `zakup.gov.kz`, `v3bl.goszakup.gov.kz`, проверка публичных DNS-адресов, ограничение 50 МиБ, ограниченные редиректы, удаление частичного файла.
- HTML/ошибку вместо ожидаемого документа нельзя выдавать за успешно распознанный текст.

### 15.3. Tenderbot — исследовательская интеграция

Документация: `https://api.tenderbot.kz/api/external/docs/v1`. База: `https://api.tenderbot.kz/api/external/v1`.

Ключ владельца сохранён локально в игнорируемом `data/tenderbot.env`, переменная `TENDERBOT_API_KEY`. В работающий Compose-продукт адаптер не внедрён. Не подменять им основной источник без отдельного решения.

Проверены:

- `GET /lots` — поиск;
- `GET /lots/{id}/files` — документы;
- справочники способов и площадок;
- Bearer-авторизация работает.

Особенности:

- `query[]` объединяется по ИЛИ; строка описана как единая фраза;
- поиск использует больше текста, чем отдаётся в кратком `description`;
- документация также заявляет поиск по названию/описанию объявления;
- исключения — `exclude_words`;
- `active`/`completed` — обобщённые статусы, без документированного точного соответствия нашим числовым статусам;
- сортировка по возрастанию ID, курсор `last_id`/`links.next`;
- лимит до 100; общее число всей выдачи не возвращается, `meta.count` относится к странице;
- для подсчёта пройдена вся цепочка страниц;
- группа способов принимается как `method_ids[]=493,501`; строка `method_ids=493,501` и отдельный код `493` в опыте отклонялись;
- `exact_match=true` строкой был отклонён, `exact_match=1` принят, но для «клавиатур» набор не изменился. Не считать точную семантику подтверждённой;
- отдельный метод поиска внутри файлов в изученной документации не найден;
- использовать ключ только на `api.tenderbot.kz`; при скачивании файлов с иных доменов не пересылать Authorization.

### 15.4. Старый портал и OWS

`goszakup.gov.kz` сейчас перенаправляет на `zakup.gov.kz`. `old.goszakup.gov.kz` продолжает обслуживать старый интерфейс. Общая авторизация и переход через NCALayer не означают одинаковый API.

По официальному сообщению от 06.10.2026, с 07.10.2026 ЗЦП перенесены на ЕПЗ, остальные способы продолжают проводиться на ЭГЗ.

Официальные сервисы OWS: `https://ows.goszakup.gov.kz/v3/`, REST и GraphQL. Документированы лоты, пункты плана, дополнительные описания, документы и журнал изменений. Есть связи `Lots → Plans`, признак объединённого лота и идентификаторы исходных систем.

Запросы к V2/V3 REST и V3 GraphQL без собственного токена проверены: 401. Требуется токен OWS; ключ Tenderbot и сессия NCALayer его не заменяют. Доступ следует получать по официальной процедуре ЦЭФ. Наличие токена, стоимость, квоты и фактическую полноту нового адаптера не выдумывать.

## 16. Результаты сравнения с Tenderbot

Все цифры ниже — **снимки исследования 28.10.2026**, а не постоянные показатели и не SLA. По мере появления закупок число Tenderbot менялось: 107 → 111 → 116.

### 16.1. Сопоставление строк

На одном из этапов:

| Показатель | Количество |
| --- | ---: |
| Наша выдача при глубине 500 | 16 |
| Полная проверенная выдача Tenderbot | 116 |
| Совпали по нормализованным номеру объявления и номеру лота | 13 |
| Только у нас | 3 |
| Только у Tenderbot | 103 |

У 103 строк первоисточники: 62 ссылки `goszakup.gov.kz`, 41 — `old.goszakup.gov.kz`. Других площадок не обнаружено. Все имели префикс госзакупа в номере объявления Tenderbot.

В этих 116 строках не обнаружены повторы ID, пары «объявление + лот», базового номера внутри объявления или одинаковых позиций по проверенному сочетанию названия/суммы/количества/заказчика. Это вывод о данной выборке, не доказательство отсутствия дублей во всей системе Tenderbot.

### 16.2. Почему строки отсутствовали у нас

- Для 100 из 103 строк объявления найдены прямым запросом в нашем публичном API.
- 72 строки сопоставлены с исходными номерами лотов в списках; с учётом вложенных пунктов плана удалось сопоставить 96 из 103. Остальные требуют дальнейшего уточнения идентификаторов/охвата.
- В свежем окне последних 500 кандидатов не было объявлений этих 103 строк. Для найденных исходных объявлений даты публикации были раньше границы окна.
- По доступным текстам: у 52 строк совпадение оказалось в дополнительных описаниях, у 22 — в названии/кратком описании лота, у 19 — только в названии объявления. Для 3 сопоставленных строк совпадение в проверенном API-тексте не установлено; ещё 7 не были достаточно сопоставлены для такого вывода.
- Эти причины пересекаются: отсутствие в глубине и иной текст поиска не являются взаимоисключающими категориями.
- У 16 строк Tenderbot подтверждена связь с позициями внутри 7 объединённых лотов. Считать их дублями нельзя; это разная единица отображения.

Пример объединения: в объявлении `17855971-1` источник возвращает лот `43712725-ОЛ-ЗЦП1` с ковриком и мышами в пунктах плана; Tenderbot показывает позиции отдельно.

### 16.3. Проверенные примеры текста

## 20. Запуск, обновление и эксплуатация

### 20.1. Первичная установка

Требуются Docker Desktop с работающим Linux engine/WSL 2 и Python 3.11+ для локальных скриптов. На текущем компьютере базовая среда уже установлена; не переустанавливать её автоматически.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e '.[dev]'
.\.venv\Scripts\python.exe scripts/setup_local.py
docker compose up -d --build
docker compose exec web python manage.py sync_references
docker compose exec web python manage.py sync_cities
```

`setup_local.py` создаёт `.env` и первичные данные входа, не должен перезаписывать существующую конфигурацию. `initialize` применяет миграции и сохраняет пароль уже существующего администратора.

### 20.2. Обновление существующей установки

```powershell
docker compose build web
docker compose run --rm --no-deps initialize
docker compose up -d --no-deps web worker telegram
docker compose exec web python manage.py check
docker compose ps
```

Сначала дождаться окончания сборки, затем применять её. Изменения Python, шаблонов и JS включаются в Docker-образ; простое сохранение файла на Windows не обновляет запущенный контейнер.

При работающем туннеле, после сборки и миграций:

```powershell
docker compose --env-file .env --env-file data/tunnel.env -f compose.yaml -f compose.tunnel.yaml up -d --no-deps web tunnel-web worker telegram
```

Overlay использовать только если локальные файлы туннеля существуют и публичный доступ действительно нужен.

### 20.3. Остановка и хранение

Для обычной остановки использовать `docker compose stop`, для запуска — `docker compose start`. Не выполнять `down -v`, удаление томов или рекурсивное удаление `data` ради обновления.

Резервная копия должна включать PostgreSQL и том документов. Наличие файлов без БД или БД без файлов не является полноценным восстановлением. Автоматизированный процесс резервирования и проверка восстановления пока требуют отдельной работы.

### 20.4. Переменные окружения

`DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`, `DJANGO_SUPERUSER_USERNAME`, `DJANGO_SUPERUSER_PASSWORD`, `DJANGO_ALLOWED_HOSTS`, `REDIS_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`.

Для HTTPS: `CSRF_TRUSTED_ORIGINS`, `HTTPS_ENABLED`, `TUNNEL_HOST`. Для локальных тестов: `TENDER_SQLITE`, `DJANGO_SECRET_KEY`. Значения секретов не включать в ТЗ.

### 20.5. Туннель

Используется Cloudflare Quick Tunnel с отдельным контейнером `tender-search-tunnel` и `tunnel-web`.

- Текущий URL читается из игнорируемого `data/tunnel-url.txt`.
- Не зашивать случайный `trycloudflare.com` hostname в код и документацию как постоянный адрес.
- Точный hostname и HTTPS-origin задаются конфигурацией.
- Secure-cookie публичной службы отделены от обычного localhost.
- Для постоянной эксплуатации нужны отдельное размещение, стабильный домен и HTTPS.

1. Новый поиск: ИЛИ, глубина 500, группа «Приём открыт», обычный ЗЦП.

## 22. Следующие этапы для агента

### Решения, которые ещё не приняты

Следующие варианты не считать уже согласованной реализацией:

- включать ли название объявления в обычный поиск наряду с текстом конкретного лота;
- показывать ли пункты плана отдельными строками или раскрывать их внутри объединённого лота;
- оставлять ли вложенные статусы и способы после завершения сравнения;
- расширять ли способ закупки по умолчанию с обычного ЗЦП на всю группу;
- какой период и какие способы охватывает первоначальный локальный индекс;
- подключать ли OWS после получения отдельного доступа;
- как долго хранить документы кандидатов, которые не добавлены в избранное.

Для каждого решения агент готовит конкретный вариант с влиянием на выдачу, число запросов, хранение данных и сохранённые профили. Простое равенство количества с Tenderbot не является критерием правильности.

### P0. Полнота и оптимизация дополнительных описаний

**Проблема:** текущий поиск снова обходит только последние N кандидатов; старые, но активные закупки могут не попасть в проверку никогда. `q` не даёт надёжного полного набора.

Требуется спроектировать отдельный сбор и локальный индекс активных закупок:

1. Разделить получение/обновление данных и пользовательское сопоставление.
2. Иметь сохраняемый курсор/границу обхода, а не каждый раз начинать и заканчивать первыми 500–1100 записями.
3. Сделать начальное заполнение активной базы наблюдаемой фоновой задачей с отменой, продолжением и состоянием покрытия.
4. Получать одно объявление один раз для связанных лотов, использовать общий кэш и не повышать rate limit без подтверждения.
5. Обрабатывать новые и изменившиеся записи инкрементально, с перекрытием границ и дедупликацией при нестабильной offset-пагинации.
6. Рассмотреть журнал изменений OWS при получении собственного токена; не считать его доступным заранее.
7. Отделить быстрый поиск по уже известному индексу от состояния ещё не загруженного покрытия.
8. Ограничивать обработку активными закупками и согласованным периодом, а не загружать всю историческую БД без необходимости.
9. Обеспечить справедливое разделение очередей поиска, файлов и статусных событий при сохранении общего ограничителя запросов.

**Приёмка:** контрольное активное объявление за пределами первых 1100 обнаруживается после заполнения индекса; повторные поиски не перекачивают тот же массив; сетевой сбой не теряет курсор; отображение полноты соответствует фактическому покрытию.

### P0. Воспроизводимое сравнение источников

- Зафиксировать время, ключевые слова, способы, исходные статусы, сроки и единицу учёта.
- Сопоставлять объявление, лот и пункт плана с отдельными внутренними/external ID.
- Разделять реально отсутствующие данные, другую семантику текста, задержку индекса и ограничение глубины.
- Не добиваться числа 116 искусственным размножением строк.
- Не подключать к рабочему поиску другие площадки только ради равенства количества.
- Не менять молча область поиска на название объявления: это добавляет, например, папки из общего объявления про мыши. Область должна быть явно согласована.

### P1. Объединённые лоты и интерфейс групп

Продолжить исследование отображения вложенных позиций. Допустимый вариант — один реальный лот с раскрываемыми совпавшими пунктами плана. Отдельное превращение каждой позиции в самостоятельный Lot требует решения владельца и правильной модели связи.

После проверки качества владелец отдельно решит, оставлять ли вложенные статусы и способы. Пока сохранить существующую возможность подробного выбора.

### P1. Производственная надёжность

- Диагностика зависших задач и lease, восстановление после перезапуска.
- Наблюдаемость очереди, ошибок API и удаления файлов без вывода секретов.
- Очистка устаревшего кэша и политика хранения истории.
- Проверяемые резервные копии и восстановление.
- Более предсказуемая доставка пользовательских статусных подтверждений при длинном поиске/скачивании в одном worker.
- Тесты конкурентного добавления/удаления общих файлов и повторных задач.
- Проверка корректного отката/отмены при закрытии дневного окна мониторинга.

### P2. Извлечение текста и поиск в файлах

1. На реальном наборе русских и казахских документов сравнить pypdf и Microsoft MarkItDown. Прямое сравнение двух обработчиков ещё не выполнено.
2. Сначала поддержать PDF с текстовым слоем и DOCX; явно отмечать неподдерживаемые/защищённые файлы.
3. Сохранять текст, версию, источник, страницу PDF или логический фрагмент DOCX, статус обработки и ошибку.
4. Нормализовать переносы и пробелы, сохраняя исходный текст и возможность показать доказательство совпадения.
5. При изменении файла создавать новую версию и не считать старую извлечённую копию актуальной без проверки.
6. Для сканов подключать локальный OCR с русским/казахским языками, ограничением времени, памяти и количества страниц.
7. Не запускать парсинг недоверенных файлов внутри web-процесса.
8. Не заменять ошибки распознавания на «совпадений нет».
9. Определить правила хранения файлов кандидатов вне избранного: нынешняя очистка удаляет всё, что больше не нужно избранному.
10. До широкого документного обхода определить обязательные способ, статус и период. Владелец предлагал запрещать включение такого поиска без способа и статуса; отдельной функции с такой валидацией сейчас нет.

Условие «находить новые закупки, где слово есть в документах, но отсутствует в заголовке» обсуждено как будущий сценарий. Он не реализован отдельным режимом. Текущий обычный поиск намеренно сохраняет и совпадения в названии.

**Приёмка будущего документного поиска:** совпадение в текстовом PDF или DOCX найдено с указанием файла и страницы/фрагмента; совпадение только в скане найдено после OCR с соответствующей отметкой; файл соседнего лота не создаёт ложное совпадение; ошибка скачивания/разбора видна как ошибка, а не как отсутствие слова. В отдельном режиме «только в документах» лоты с совпадением в заголовке исключаются по согласованному режиму сопоставления. Проверки обязательных статуса и способа выполняются на сервере, а не только отключением элемента интерфейса.

### Формат сдачи очередного этапа

Каждый этап завершать коротким отчётом: реализованное поведение, изменённые модули/миграции, выполненные проверки с результатами, способ обновления работающей установки и оставшиеся ограничения. Для оптимизации фиксировать на одинаковом наборе данных количество HTTP-запросов, длительность первого и повторного обхода, размер кэша и полноту покрытия. Численные целевые сроки согласовать после измерения исходного состояния; не выдавать прогноз скорости за измеренный результат.

## 23. Порядок работы следующего ИИ-агента

1. Уточнить текущую задачу по последнему сообщению владельца; документ не является разрешением выполнить весь backlog сразу.
2. Проверить актуальное состояние файлов, запущенных служб и миграций без чтения секретов в вывод.
3. Для продолжения поиска начать с `search_service.py`, `procurement_groups.py`, `forms.py` и материалов сравнения.
4. Перед миграцией значений профилей учитывать старые исходные статусы и новые токены `open:`/`upcoming:`. Не подменять персональные настройки defaults.
5. Сохранять тестами изоляцию владельцев, корректность сроков, отсутствие повторных отправок и безопасную очистку файлов.
6. Не увеличивать параллелизм источника ради быстрого демонстрационного результата.
7. При наличии ошибки сообщать реальное состояние и сохранять уже полученные результаты.
8. После изменения рабочих модулей пересобрать образ, применить необходимые миграции и обновить нужные службы. Изменения документации сами по себе не требуют перезапуска приложения.
9. Кратко сообщать владельцу результат, что проверено и какое ограничение осталось. Без обязательного скриншота каждого шага.
10. Напоминания, созданные в приложении Codex, не являются задачами Celery продукта. Не создавать их дубликаты как часть этого ТЗ.
